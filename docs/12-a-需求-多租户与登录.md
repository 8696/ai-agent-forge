## A · 多租户基础

### A1 · 多租户数据隔离

**需求**：每个租户数据严格隔离，查询不跨租户。

**使用技术**：

- MySQL 8.0（InnoDB 引擎、utf8mb4 字符集）—— ✅ **2026-10-26 由迁移
  `src/migrations/027-normalize-charset.ts` 显式规范**（字符集 `utf8mb4` /
  排序规则 `utf8mb4_unicode_ci` / 引擎 `InnoDB`），**不依赖 MySQL 服务器 /
  数据库的默认值**
- Sequelize 6.x + sequelize-typescript（装饰器风格）
- **运行时强制**（2026-10-25 补）：请求级租户上下文（`node:async_hooks` 的 `AsyncLocalStorage`，
  `src/lib/tenant-context.ts`）+ Sequelize 全局钩子（`src/lib/tenant-scope.ts`）
  —— 查询发出前**自动补上 `tenant_id` 过滤**，人不用记得加
- **架构约束测试**（`tests/unit/tenant-isolation-guard.test.ts`）——
  静态扫描源码，拦下运行时兜不住的情况

> ✅ **2026-10-25 补上「运行时强制」**。原来这里只有一条静态约束测试，
> 也就是说**隔离是「靠人记得加过滤」**——漏写一次 `tenant_id` 就是跨租户泄露，
> 而且静态测试拦不住「加错了」（它只问「有没有出现 tenant_id 这个词」，
> 不问「是不是这个租户的」）。
>
> 现在的三层防线：
>
> | 层 | 在哪 | 拦什么 |
> | --- | ---- | ------ |
> | ① 运行时钩子 | `src/lib/tenant-scope.ts` | **忘了加过滤** —— 自动补上 `tenant_id` |
> | ② 约束测试 | `tests/unit/tenant-isolation-guard.test.ts` | where 形状不对（数组 / 顶层 `Op.or`）、**写死租户 id** |
> | ③ 白名单 | 同上的 `ALLOWED_NO_TENANT_FILTER` | 登记「这条查询本来就不该带租户过滤」，要写清理由 |
>
> 钩子挂在四个 Sequelize 钩子上：`beforeFind`（findAll / findOne / findByPk /
> findAndCountAll）、`beforeCount`、`beforeBulkUpdate`、`beforeBulkDestroy`。
>
> ⚠️ **`Model.aggregate` / `Model.sum` 不触发任何 Sequelize 钩子** ——
>    这两个方法**不受租户隔离保护**，用到的地方必须自己带 `tenant_id`。
>    全仓唯一的 `.sum()` 在 `src/gateway/system/tenant-routes.ts`（单租户成本统计，
>    显式带了 `tenant_id`）；平台方的**跨租户**统计走的是 `src/services/system-stats.ts`
>    的原生 SQL（不走 ORM，天然跨租户）。
>
> ⚠️ **运行时强制可以整层关掉**（`.env` 的 `TENANT_SCOPE_ENFORCE`，默认 `true`，
>    见 `src/config.ts` / `src/lib/tenant-scope.ts`）——
>    关掉就退回「全靠人记得加过滤」的状态（钩子直接 return，不补 `tenant_id`）。
>    ⚠️ **这个口子的处理方式跟 D4 把脱敏开关摘掉不一样**：脱敏是「写进历史库前的最后一道
>    防线」，没有第二层能兜住，所以干脆不给开关；而租户隔离关掉后**还有约束测试
>    + 静态扫描挡着**（查错形状、写死租户 id 仍会被测试拦下），出事能靠测试发现，
>    所以留了这个止血开关 —— 默认开着，只是「上线后出问题先关掉止血、修好再打开」用。
>
> ⚠️ **平台方（system 子系统）刻意不设租户上下文** —— 它本来就要跨租户看数据
>    （租户列表、跨租户 KPI）。admin / customer / 对外 API 三个命名空间都设了。
>
> ⚠️ **显式写了别的租户 → 抛 500**（`TenantIsolationError`）：不是 403，
>    因为那不是「用户没权限」，是**代码写错了**——报 500 是故意让它在错误率指标里显眼。

**验收**：

- 建两个租户 T1 / T2，各传一份文档
- T1 admin 调 `listDocuments(T1)` 只能看到 T1 的文档
- 直接 `Document.findAll()`（不带 scope）—— ✅ **运行时钩子自动补上 `tenant_id`**，
  拿不到别的租户的数据
  —— 同时由约束测试守住「查询形状」和「别写死租户 id」
- ✅ 约束测试的模型清单**从 `src/models/` 自动推导**（不再手写）——
  新增模型只要有 `tenant_id` 列就自动进清单，漏登记不可能发生
  （2026-10-25 之前手写 17 个，漏了 `TenantSetting`，那个模型的 4 处查询从没被扫过）
- ✅ 约束测试的查询方法清单补全（`findAndCountAll` / `bulkCreate` 都曾经漏扫）
- ✅ 约束测试**剥离注释后再扫** —— 文档里引用一句 `Document.findAll()` 不算一次查询

### A2 · SaaS 平台方建租户 + 自动初始化 admin

**需求**：SaaS 平台方建租户时自动写 `tenants` + 第一个 admin 账号。

**使用技术**：

- Koa 路由（system 子系统前缀）
- Sequelize 事务
- bcrypt 密码哈希（cost=12）
- Zod 校验租户号格式

**验收**：

- POST 创建租户带正确 body → 返回租户 + admin 信息
- 数据库里 tenants 有 1 条新记录，users 有 1 条 `role='admin'` 的记录
- code 重复提交 → 返回 400 「租户号已被使用」
- 跨子系统鉴权：用非 system 角色的 token 调用 → 401
  —— ✅ **2026-10-26 补齐端到端用例**（「code 重复 → 400」「非 system token → 401」）

### A3 · 后台用户管理（admin 子系统内部，含创建 customer）

**需求**：租户 admin 创建本租户内的用户——创建时可指定角色（admin 子系统入口可下发 admin / customer 两类用户）；列 / 改邮箱 / 重置密码 / 删全部限定在本租户范围内。

**使用技术**：

- Koa 路由（admin 子系统前缀）
- bcrypt 密码哈希
- Zod 校验（`createUserSchema` 收 `role: 'admin' | 'customer'`；`roleSchema` 显式拒收 `agent`——`agent` 是历史 ENUM 值，MVP 不开放）
- 跨租户隔离：`where: { tenant_id: ctx.state.adminUser.tenant_id }`（强制加过滤）
- 自删防御：删除时校验不能删自己；前端按当前用户 id 把删除按钮 disabled

**验收**：

- admin 创建 3 个 admin 角色用户（实际业务：不同 admin 共存）
- admin 创建 2 个 customer 角色用户（前台用户由租户后台代建；不再只能 customer 自注册）
- 三个用户能分别用对应入口登录（同租户号 + 不同邮箱）
- 跨租户创建用户被禁止（`tenant_id` 永远从 token 拿，不接受 body）
- 自删防御：列表点自己的删除按钮 → 按钮 disabled；直接调 API 也返回 400「不能删除自己」
  —— ✅ **2026-10-26 补齐端到端用例**（admin 创建 **admin 角色**用户，不只 customer 角色）

### A4 · 三层登录 + 鉴权（每套子系统自闭环）

**需求**：3 个登录入口（system / admin / customer），每个子系统自己一套 login / me / change-password，前后端 URL 前缀对齐。

**使用技术**：

- Koa 路由（3 套独立端点，无共享 auth namespace）
- JWT（`jsonwebtoken`）：system 用 `{sub, role:'system'}`；admin/customer 用 `{sub, tenant_id, role}`
- bcrypt 密码哈希
- Zod 校验
- 5 次失败 → 锁定 15 分钟
- 统一 401 响应（不区分「用户不存在」vs「密码错」，防账号枚举）

**端点**（每个子系统各一套，**不共用**）：

| 子系统    | 前缀                    | 端点                                                |
| --------- | ----------------------- | --------------------------------------------------- |
| system    | `/api/v1/system`        | `POST /login` · `GET /me` · `POST /change-password`  |
| admin     | `/api/v1/admin`         | `POST /login` · `GET /me` · `POST /change-password`  |
| customer  | `/api/v1/customer`      | `POST /login` · `GET /me` · `POST /change-password`  |

> ⚠️ **`/me` 和 `/change-password` 之前被删过**（代码注释写着「前端未用」），
> 结果是这个需求的 19 个验收用例缺了 6 个，而且 `must_change_password`
> 这个字段**从建表起就没人消费** —— 平台方重置租户 admin 密码后，
> 用户拿着临时密码长期用下去，没人被要求改。2026-10-25 补上（见下）。

**「必须先改密」的闸门**（2026-10-25 补）：

- 平台方建租户 / 重置 admin 密码时置 `must_change_password=true`
- 这个标志**签进 JWT**（`src/lib/jwt.ts`）→ 每个请求都能零 DB 往返地检查它
- 闸门在 `src/gateway/password-change-gate.ts`：被标记的账号，
  **除 `/me` 和 `/change-password` 外的所有请求一律 403**
  - 用 **403 不用 401**：401 会让前端以为「登录过期」把人踢回登录页，
    而他正被要求改密 —— 踢回去就成了死循环
- 改完密码后端**换发一枚新 token**（旧 token 里还带着标志），前端替换掉即可
- 前端：登录时发现标志 → 强制跳 `/admin/change-password`（customer 同理）；
  页面是全屏的（不套后台外壳），三套子系统共用一个组件但**路由各归各**
  - ⚠️ **system 子系统没有这条「强制改密」流程**：`system_users` 表**没有
    `must_change_password` 列**（平台方账号由平台自己管理，没有「被临时重置密码」
    这个场景，见 `src/gateway/system/auth-routes.ts` 的注释）——
    所以只有 admin / customer 会被强制改密；system 侧那个改密页只是**用户自愿改**

**验收**（19 个端到端用例）：

- system 登录（正确 / 错密码 / 错邮箱 / 错误响应统一防枚举）= 4
- admin / customer 各自登录（正确 / 错租户号 / 错密码）= 6
- 跨子系统防御：admin 账号登 customer → 401；customer 账号登 admin → 401 = 2
- 各自 me 端点正确（admin/customer 200，system 调 admin 的 me → 401，admin 调 customer 的 me → 401）= 4
- 5 次失败 → 锁定（DB 状态正确 + 正确密码也 401）= 2
- 成功后 failed_login_count 清零 = 1
- 改密码（admin 自己改 + 改后 me 仍 OK）= 2
  - ✅ 已落地（2026-10-25）：`POST /api/v1/{admin,customer,system}/change-password`
    + `GET /api/v1/{admin,customer,system}/me`
    （集成测试 `tests/integration/auth-me-change-password.test.ts`）

> **反例**（禁止）：
>
> - ❌ 一个端点多种身份（用 `login_type` 字段区分）
> - ❌ 两个子系统共用一个 change-password 端点
