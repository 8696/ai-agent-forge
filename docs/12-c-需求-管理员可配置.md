### C1 · 知识库管理 ✅ 已落地（2026-10-20）

**需求**：admin 上传 PDF / Markdown / TXT；自动拆块 + Embedding + 入向量库；能查看文档列表和每篇的块数。

**使用技术**：

- koa-body（multipart 文件上传）+ formidable（大小上限 / 落 tmp）
- pdf-parse v2（PDF 解析，`pageJoiner: ''` 关掉页码标记 + 保留每页文本）；MD / TXT 走 UTF-8 严格解码，失败退回 latin1 兜底
- 拆块（**结构感知**，2026-10-27 改版）：先解析成带类型的元素序列（Markdown 走 AST / PDF 按页 / TXT 按段）→ 按标题分节 → 节内按元素聚合成块 → 块首拼标题路径面包屑（800 字 / overlap 150）
- Embedding API（OpenAI 兼容 REST，按 `LLM_PROVIDER` 走对应端点）
- Qdrant（向量写入 + `tenant_id` / `doc_id` keyword payload index）
- BM25（nodejieba 分词，进程内索引）
- MySQL `documents` 表（存元数据 + 状态 + 块数）

**接口**（`src/gateway/admin/knowledge-routes.ts`，前缀 `/api/v1/admin`，要求 admin 角色）：

| 方法   | 路径                     | 说明                                                         |
| ------ | ------------------------ | ------------------------------------------------------------ |
| GET    | `/knowledge`             | 文档列表（含块数 / 分页 / 状态筛选 / 关键词搜索 / 块数统计） |
| POST   | `/knowledge/upload`      | 上传 → 解析 → 拆块 → Embedding → 入库（**同步**）            |
| POST   | `/knowledge/:id/reindex` | 复用磁盘原文件重新跑整条索引链路                             |
| DELETE | `/knowledge/:id`         | 删 Qdrant points + BM25 索引 + 磁盘文件 + DB 行              |
| GET    | `/knowledge/:id/chunks`  | **看一篇文档的切片**（分页 · 带「人工编辑」标记）2026-10-27        |
| PATCH  | `/knowledge/:id/chunks/:index` | **改一块的文字**（重算该块向量）2026-10-27                 |
| POST   | `/knowledge/:id/chunks/:index/split` | **把一块拆成两块**（按光标位置）2026-10-27        |
| POST   | `/knowledge/:id/chunks/merge` | **把连续的几块合并成一块** 2026-10-27               |
| POST   | `/knowledge/:id/chunks/:index/reset` | **还原成程序生成的文本**（撤销人工改动）2026-10-27 |
| POST   | `/knowledge/search`      | 混合检索（向量 + BM25 → RRF），**不调 LLM**                  |

> ⚠️ **列表响应里的统计只有 3 项**：后端的 `stats` 对象给的是**块数**三档
> （`chunk_total` / `bm25_chunk_total` / `qdrant_points`）——
> **「文档总数」不在 `stats` 里**，它来自分页字段 `pagination.total`
> （前端自己取来显示）。别把返回值当成 4 个 stats 字段。

**页面**：`/admin/knowledge/documents`（文档管理）、`/admin/knowledge/test`（检索测试）、
`/admin/knowledge/chunks`（切片浏览 · 2026-10-27），详见 `04-c` §5.2 / §5.3 / §5.13。

**验收**：

- ✅ 上传 .md / .txt → 请求返回时状态已是 `ready`，带 `chunk_count`
- ✅ 上传 .pdf → 文本提取 + 索引成功，额外返回 `pages`
- ✅ Qdrant 里能查到对应向量（collection 维度按 Embedding provider 配置，换 provider 维度变了要删库重建）
- ✅ 检索测试页能命中本租户的文档，每条标出「语义第 N / 关键词第 N」
- ✅ 跨租户防御：tenantA 的 token 检索不到 tenantB 的文档，直接拿别人的 doc_id 查 / 改 / 删都返 404
- ✅ audit_logs 写了 `DOCUMENT_UPLOAD` / `DOCUMENT_INDEX_FAILED` / `DOCUMENT_DELETE`
- ✅ **切片浏览页（2026-10-27）**：能看到一篇文档被切成的每一块（序号 / 字数 / 标题路径 / 正文）；
  跨租户拿别人的 doc_id 查切片同样 404
- ✅ **人工编辑切片（2026-10-27）**：改一块 → **该块向量重算**（没改的块复用旧向量，
  接口返回 `embedded` / `reused`）→ 同步 BM25 → 写 `document_chunks` 权威副本；
  拆 / 合 / 还原同理；编辑留审计（`DOCUMENT_CHUNK_EDITED` / `_SPLIT` / `_MERGED` / `_RESET`）
- ✅ **重新索引保留人工编辑（2026-10-27）**：按源区间重叠度搬回新块；
  搬不回来的在返回体的 `unmatched_edits` 里报数，**不静默丢弃**

**自动化测试**：

- `tests/unit/{chunk,elements,bm25,hybrid-search}.test.ts` —— 拆块 / 元素层 / BM25 / RRF 融合的纯逻辑
- `tests/unit/document-chunks.test.ts` —— 切片编辑的纯逻辑（拆分位置 / 面包屑处理 / 合并）
- `tests/integration/admin-knowledge.test.ts` —— 5 个端点 + 跨租户隔离（19 个用例，
  **会真的调 Embedding API 并往 Qdrant 写真数据，跑完自动清理**）
- `tests/integration/document-chunk-edit.test.ts` —— 切片编辑端到端
  （**embedding 被 mock，零费用**）：索引写副本 → 改 → 拆 → 合 → 重新索引保留编辑 → 跨租户 → 删文档清副本

### C2 · 工具管理 ✅ 已落地（2026-10-25 · 内置 mock 工具）

**需求**：租户 admin 在后台注册 / 查看 / 启停本租户可用的工具。
注册了工具，AI 才能调 —— 调用怎么实现见 [12-b](./12-b-需求-ai对话能力.md) §B3。

**当前状态**：✅ **已实现**（2026-10-25）。

**支持两类**（用户 2026-10-26 裁定）：

| type | 状态 | 说明 |
| ---- | ---- | ---- |
| `builtin` | ✅ 可执行 | 平台自带实现（8 个） |
| `http` | ✅ 可执行（**本地 mock**） | 保留 url / method 的配置形状，但**平台不真的发请求**，按 `(租户, url, method, 入参)` 确定性生成响应。实现见 `src/tools/http-mock.ts` |
| `mcp` | 🚫 **不做** | **跨系统** —— 要用 MCP，租户那边得自己跑一个 MCP server |

⚠️ **`http` 不是「真的调租户的接口」** —— 真出网是跨系统的事，
且出网安全策略没定（`http` 工具的正常用法恰恰是调租户内网）。
完整裁定见 [12-e 需求裁定表](./12-e-需求-业务接入与平台运营.md) #1 / #2。

**这一页真正的价值是「改描述」**：工具的描述是**给模型看的**，
它直接决定模型调不调这个工具。同一个内置工具，餐饮租户该写「查这个门店的订单」，
物流租户该写「查运单轨迹」。所以描述是租户唯一能「调教模型」的手柄，
改完**下一轮对话立刻生效**（每轮对话都重新读库，不走进程缓存）。

**使用技术**：

- MySQL `tools` 表（`tenant_id` / `name` / `description` / `type` / `config` JSON /
  `enabled` / `requires_confirmation` / `created_by` / **`updated_by`**），
  迁移 `022-create-tools`；`updated_by`（最后修改人）由迁移 `026-add-tool-updated-by` 追加
- `config` JSON 装不同类型的配置：
  `builtin` 装工具标识；`http` 装 `url` / `method` / `headers` / `body_template` /
  入参 schema；`mcp` 装 `mcp_server_url` / `mcp_server_path` / `headers`
  （⚠️ **`http` / `mcp` 的 `headers` 里有密钥，将来落地时必须加密**
  —— 复用 `src/lib/crypto.ts` 的 AES-256-GCM。本轮只有内置工具，不涉及密钥，
  所以 `config` 保持明文 JSON）
- 前端：AntD Table + 注册/编辑抽屉（`/admin/tools`）

**接口**：

| 方法   | 路径                            | 说明                                        |
| ------ | ------------------------------- | ------------------------------------------- |
| GET    | `/api/v1/admin/tools`           | 工具列表（name / type / 状态 / 描述）       |
| GET    | `/api/v1/admin/tools/builtins`  | 平台内置工具清单（注册时的下拉框）          |
| GET    | `/api/v1/admin/tools/:id`       | 单条工具详情                                |
| POST   | `/api/v1/admin/tools`           | 注册工具（本轮只允许 `builtin`）           |
| PATCH  | `/api/v1/admin/tools/:id`       | 改描述 / 启停 / 敏感标记                    |
| DELETE | `/api/v1/admin/tools/:id`       | 删                                          |
| POST   | `/api/v1/admin/tools/:id/test`  | 试连一次（用内置实现的样例入参真跑一遍）    |

**页面**：`/admin/tools`（工具管理）—— 详见 [04-c](./04-c-ui-后台管理页面.md) §5.5

**验收**（✅ 2026-10-25 落地）：

- ✅ 注册一个 `builtin` 工具 → 试连能通，`/test` 返回工具的真实输出 + 耗时
- ✅ 禁用一个工具 → 下一轮对话的 tool 列表里不再有它
- ✅ 工具名在租户内唯一；重名返回 400（`UNIQUE (tenant_id, name)` 兜底）
- ✅ 调用名必须合法标识符（小写字母开头，只能含小写字母 / 数字 / 下划线 / 短横线）——
  模型调用时用的就是这个名字，中文/空格会调不出来
- ✅ 跨租户隔离：B 租户的 admin 看不到也改不了 A 租户的工具（按 id 取也是 404）；
  但**同名工具在两个租户可以各注册一个**（唯一性是租户内的）
- ✅ 审计：注册 / 改 / 删 / 启停工具都写 `audit_logs`
  （`TOOL_CREATED` / `TOOL_UPDATED` / `TOOL_ENABLED` / `TOOL_DISABLED` / `TOOL_DELETED`）
- ✅ `config` 里的敏感字段接口永不返回明文（2026-10-26 落地）——
  工具列表 / 详情接口只回 `url` / `method`，**不回 `mock_response` 原文**
  （那是租户自己填的响应内容，可能含敏感信息）；审计日志同样只记 `url` 不记原文
- 🚫 **注册一个 MCP 服务 → 能列出该服务提供的工具** —— **不做**（跨系统，见 [12-e 裁定表](./12-e-需求-业务接入与平台运营.md) #1）

**已知边界**：

- **编辑时不能改调用名和内置实现** —— 改调用名等于换了个工具，模型的历史认知全废。
  需要换实现的话，删掉重新注册一个
- **内置工具是 mock** —— 订单 / 商品 / 物流 / 优惠券 / 退款单都是按租户 + 编号确定性生成的假数据

#### 工具调用记录 ✅ 已落地（2026-10-25）

  **唯一出口，不会漏记**；**写库失败不影响对话**（内部 try/catch 吞掉）
- 页面：`/admin/tool-logs`

**接口**（`src/gateway/admin/tool-log-routes.ts`）：

### C3 · 提示词配置 ✅ 已落地（2026-10-21）

**需求**：每个租户自定义系统提示词；可版本管理。

**使用技术**：

- MySQL `prompt_versions` 表（`content` 存正文，**不是**指向代码文件的 file_path ——
  指向文件的话后台只能「选版本」不能「编版本」，改提示词还得发版）
- 版本流转 draft → production → archived，**单租户同时只有一个 production**
- production / archived **不允许直接改**：已经被真实用户用过了，静默改等于让线上行为无预告地漂移；
  必须「复制成新草稿 → 发布」
- 每轮对话读库解析（不缓存），所以发布后**立即生效**（docs/12-e §E2）
- **「发布」与「写生效指针」在同一个事务里**（2026-10-25 补）：
  版本置 `production` 与写租户生效指针（`tenant_settings.prompt_version`）
  是**一次事务提交的两步** —— 分成两步会出现「版本已经标成 production 了，
  但指针还指着旧的」的**半成功**状态，租户明明点了发布，提示词却永远不生效。
  连带 D1 的「故意改坏提示词 → 分数跌 10%」也触发不了（压根没生效）
- 内置默认提示词在 `shared/prompts/chat/system-default.ts`（租户没建版本时兜底）

**接口**（`src/gateway/admin/config-routes.ts`，前缀 `/api/v1/admin`，admin 角色）：

| 方法   | 路径                                    | 说明                            |
| ------ | --------------------------------------- | ------------------------------- |
| GET    | `/config/prompts`                       | 版本列表（不含正文，避免一次拉几十 KB） |
| GET    | `/config/prompts/default`               | 内置默认提示词（新建版本时的初始值） |
| GET    | `/config/prompts/:version`              | 取单个版本正文（编辑区按需拉）    |
| POST   | `/config/prompts`                       | 新建草稿版本                     |
| PUT    | `/config/prompts/:version`              | 改草稿（production 会 400）      |
| POST   | `/config/prompts/:version/publish`      | 发布 → 转 production，并同步把租户配置指向它 |
| POST   | `/config/prompts/:version/rollback`     | 回滚（= 重新发布该历史版本）      |
| DELETE | `/config/prompts/:version`              | 删（production 不让删）           |

**页面**：`/admin/prompts`（左侧版本列表 + 右侧编辑器）
—— 旧文档写的 `/admin/model/prompt` **已废弃**，实际路由以本行为准

**验收**：

- ✅ 租户 A 提示词 =「你是 X 公司的客服」，租户 B 提示词 =「你是 Y 公司的客服」——
  每租户独立一套版本，互不影响
- ✅ 后台改完发布 → **下一轮对话立即生效，不用重启**（端到端实测：把提示词改成
  「夜班客服机器人，答案结尾必须加『——夜班机器人』」，发一轮对话，回答确实带上了）
- ✅ 跨租户隔离：所有查询强制带 `ctx.state.adminUser.tenant_id`
- ✅ **版本可以被评测单独指定使用**（2026-10-26 补）：D1 的 A/B 对比需要
  「用指定版本的提示词跑一次」—— 跑批接口 `POST /api/v1/admin/evaluation/runs`
  的 body 带可选的 `prompt_version`（不传 = 跟随生效指针）。
  ⚠️ **指定的版本不存在直接 400，不静默回落默认** ——
  回落会让「这一版比上一版好还是差」的对比结果**骗人**。
  详见 [12-d §D1](./12-d-需求-运维稳定.md) 与
  [12-e 裁定表](./12-e-需求-业务接入与平台运营.md) 表 4

### C4 · 模型选择 ✅ 已落地（2026-10-21）

**需求**：主对话模型可换，且能按租户分别配置。

**使用技术**：

- **Vercel AI SDK**（`ai` + `@ai-sdk/anthropic`）：`streamText()` + `createAnthropic({apiKey, baseURL})`
- **模型列表**（`tenant_models` 表）：一个租户可配**多条**，每条是一套**完整连接配置**
  （端点 + 密钥 + 采样），逐条切换「启用中」。共享连接配置的代价是「换个模型还得复制
  一遍网关和密钥」，而且「自建网关 + 官方 API 并存」根本表达不了
- **三层配置**：模型条目（租户级）→ 通用配置 KV（租户级）→ `.env` 进程默认，
  **每一项独立回落**，所以运维改一次 `.env` 能批量调，租户只覆盖自己不一样的
- apiKey 用 **AES-256-GCM 加密**落库（密钥 = `CONFIG_ENCRYPTION_KEY`），
  另存 `api_key_hint` 脱敏串；**接口永不返回明文或密文**
- baseURL 存前做 **SSRF 校验**：生产默认禁止指向回环 / 私网 / 链路本地（含云元数据
  169.254.169.254）/ CGNAT，且**逐个 DNS 解析结果校验**（防 nip.io 这类把内网 IP
  解析成域名的绕过）；dev 默认放开，自建局域网网关用 `CONFIG_ALLOW_PRIVATE_LLM_ENDPOINT=true`
- 每轮对话读库，保存后**立即生效**，不走进程缓存

**接口**（`src/gateway/admin/config-routes.ts`）：

| 方法   | 路径                        | 说明                                    |
| ------ | --------------------------- | --------------------------------------- |
| GET    | `/config/models`            | 模型列表（只有 `has_api_key` + `api_key_hint`）+ `active_chat` / `active_memory` / `active_summary`（当前生效的**三条**，每个用途一条）+ `process_defaults`（进程默认凭据的展示）/ `secret_encryption_enabled`（密钥加密有没有开）/ `notes`（给页面看的说明文案） |
| POST   | `/config/models`            | 新建（**每个 scope 的第一条**自动成为该 scope 的启用项） |
| PUT    | `/config/models/:id`        | 改（不带 `api_key` 字段 = 密钥保持原样） |
| POST   | `/config/models/:id/activate` | 切换启用（事务内保证「每租户每 scope 恰一条启用」） |
| DELETE | `/config/models/:id`        | 删                                        |
| POST   | `/config/models/:id/test`   | 按该条试连一次（不落消息表）               |
| POST   | `/config/models/check-endpoint` | 校验 Base URL 能不能用 —— 模型编辑抽屉上的「测一下这个端点」按钮直接调它（**静态校验**：URL 合法 / 协议是 http·https / SSRF 私网判定 / DNS 解析，**不会真发一次模型请求**） |
| GET    | `/config/settings`          | 通用配置（KV，带类型 / 范围 / 默认值元信息）|
| PUT    | `/config/settings`          | 批量保存（`null` = 清除覆盖回落默认）      |

**模型条目的「用途」（`usage_scope`）**（2026-10-24 补）：

每条模型条目带一个用途字段，决定它服务于哪条链路：

| 用途      | 谁在用                          | 回落                        |
| --------- | ------------------------------- | --------------------------- |
| `chat`    | 主对话                          | 平台默认（`.env`）           |
| `memory`  | B4 长期记忆的**自动抽取**（独立的一次 LLM 调用） | 对话模型 → 平台默认 |
| `summary` | B1 **会话摘要压缩**（独立的一次 LLM 调用，长对话每轮最多一次） | 对话模型 → 平台默认 |

- **每个 scope 各自一条启用项**，互不影响（切换 memory scope 不会动 chat scope）
  ⚠️ **改一条模型的「用途」有个副作用**（2026-10-26 补记）：
  代码会把这条在**旧 scope** 里的启用位去掉、再看新 scope 有没有启用项
  （没有就把它启用）—— 但**旧 scope 不会自动补一条启用项**。
  也就是说：把唯一的 chat 模型改成 summary 之后，**chat scope 变成 0 条启用项**，
  对话会静默回落到平台默认模型（不是报错，是「不声不响地换了模型」）。
  改完用途记得回「模型列表」确认一下各 scope 的启用项。
- 没配 `memory` 模型时，抽取**回落到对话模型** —— 不配也能用，行为跟没这个字段之前一样
- 意义：抽取是独立的一次 LLM 调用（实测约 2000 token），推理型模型的思考 token 全额算
  输出 token。租户单独配一条便宜模型，是唯一能压这项成本的手段

**页面**：`/admin/models`（模型列表）、`/admin/prompts`（提示词）、`/admin/settings`（通用配置）
—— **三页分开，不混在一页**。

**验收**：

- ✅ 建多条模型、切换启用 → 下一轮对话立即走启用中的那条
- ✅ 第一条模型自动成为启用项（不会出现「配了却没选中」）
- ✅ 切换只保留一条启用（单事务保证）
- ✅ **每个 scope 各自一条启用项**：切 memory / summary scope 都不动 chat scope（单事务保证）
- ✅ 配一条「会话摘要」用途的模型 → 摘要走它；不配则回落到对话模型 → 平台默认
- ✅ 配一条「记忆抽取」用途的模型 → 抽取走它；不配则回落到对话模型 → 平台默认
- ✅ 对话链路读到的是启用模型 —— 端到端实测：建模型 → 切换 → 发对话，回答正常
- ✅ 3 个子系统页脚展示「当前激活 LLM · provider · model」+「Embedding · model · NNNd」，
  数据来自 `GET /active-config`，`deepseek` 等不提供 Embedding 的 provider 显示「—」
- ✅ 租户级 model 覆盖**不暴露在页脚**（页脚是进程级）；在「模型选择」页看和切
- ✅ **「备用模型」已落地（2026-10-26）**：原规格（04-c §5.4.1）里的「备用模型下拉」
  一直是个缺口 —— 这轮补上了
  - **存储**：`tenant_models` 加一列 `fallback_model_id`（迁移 `030`），
    指向**同租户、同 scope** 的另一条模型条目
    （跨 scope 禁止：chat 的备用不能是 memory 的 —— 用途不同、成本也不同）
  - **配置**：模型编辑抽屉里一个「备用模型」下拉（候选 = 同用途、且不是自己）
  - **生效**：主模型调用失败（provider 报错 / 连不上）时自动切到它再试一次
    —— 实现见 `src/lib/llm-failover.ts`
  - ⚠️ **流式对话只在「一个内容 chunk 都还没吐出去」时才切** ——
    已经吐给浏览器的字收不回来，重切会导致内容重复，
    重复的 tool call 还会**真的执行两遍**（提交两次退款单）
  - ⚠️ **备用模型的正文照样过输出审核（D4）** —— 换了模型不等于绕过审核
  - 非流式的旁路调用（记忆抽取 / 会话摘要）**无条件切** —— 那里没有「已吐内容」的问题

> ⚠️ **与 04-c §5.4.1 原规格的差异**：原规格是「一条模型配一个备用模型下拉」，
> 实现时改成了「模型列表 + 启用切换」（更能表达「自建网关 + 官方 API 并存」）。
> **这两个不是二选一** —— 备用模型下拉这轮加回来了，两种并存：
> 列表管「手动切」，备用下拉管「自动切」。

**租户可覆盖 vs 留平台级的分界线**：

| 放租户后台 | 留平台级（`.env`） |
| --- | --- |
| 模型列表（model / Base URL / apiKey / 温度 / 输出上限 / 提示词缓存 / **用途**） | `CONFIG_ENCRYPTION_KEY`（泄密 = 全盘沦陷） |
| 提示词版本（C3，独立页面） | `CONFIG_ALLOW_PRIVATE_LLM_ENDPOINT`（租户能开就能打内网） |
| 通用配置 KV（检索条数 / 历史轮数 / 检索 token 上限 / 上下文总预算 / 输入字数上限 / 思考预算 / 记忆开关 / 摘要开关 / **重排开关** / **查询改写开关** / **多代理开关** / **首页欢迎语 / 首页推荐问题**） | SSE 心跳、估算安全垫、系统提示词兜底值（传输层 / 内部估算参数） |
| **月度 token 预算**（D3，见 [12-d](./12-d-需求-运维稳定.md) §D3） | `COST_TRACKING_ENABLED`（成本记账总开关）、`COST_BUDGET_BLOCK`（超预算是**拦截**还是**只告警**）、`COST_PRICE_TABLE`（内置价格表的覆盖） |
| **每分钟请求上限**（D5，见 [12-d](./12-d-需求-运维稳定.md) §D5） | `RATE_LIMIT_ENABLED`（限流总开关）、`RATE_LIMIT_WINDOW_MS`（窗口长度）、`RATE_LIMIT_MAX_REQUESTS` / `RATE_LIMIT_MAX_REQUESTS_PER_USER`（租户没配时的进程默认） |
| **3 项告警阈值**（p95 延迟 / 错误率 / 单条对话成本，D2，见 [12-d](./12-d-需求-运维稳定.md) §D2） | 告警的**判定口径**（统计窗口、错误率算法）留在服务端代码里，租户只能改阈值数字 |
| **重排开关**（B2，见下） | `RERANK_ENABLED`（平台总开关，硬边界）、`RERANK_API_URL` / `RERANK_API_KEY` / `RERANK_MODEL` / `RERANK_TIMEOUT_MS` / `RERANK_CANDIDATES`（端点 / 凭据 / 模型不给租户） |
| **记忆开关 / 每轮注入几条 / 记忆 token 上限**（B4，见下） | `CHAT_TEMPERATURE`、`CHAT_MAX_OUTPUT_TOKENS`（**已在模型条目里**，不再重复存一份） |
| **摘要开关 / 摘要 token 上限**（B1 摘要压缩，见下） | `CHAT_SUMMARY_ENABLED`（平台总开关）、`CHAT_SUMMARY_MAX_INPUT_TOKENS`、`CHAT_SUMMARY_TIMEOUT_MS`（传输层 / 内部参数，留 `.env`） |
| | `MEMORY_ENABLED`、`MEMORY_MAX_ACTIVE_PER_USER`、`MEMORY_MIN_CONFIDENCE`、`MEMORY_EXTRACT_TIMEOUT_MS`（平台级边界，租户改不了） |
| | `MEMORY_RELEVANCE_ENABLED`（记忆相关性排序的平台总开关）、`MEMORY_RELEVANCE_TIMEOUT_MS`（算问题向量的超时，平台级） |

> 通用配置页的**元信息在代码里**（`SETTINGS_REGISTRY`），库里只存「租户改过的值」——
> 这样类型和范围校验有代码兜底，页面也能按 registry 自动渲染，
> 加一个配置项不用碰 SQL。

**B4 记忆的四个租户级配置项**（在通用配置页的「记忆」分类下）：

| key | 名称 | 默认 | 说明 |
| --- | ---- | ---- | ---- |
| `memory_enabled` | 开启用户记忆 | `true` | 关掉后既不自动抽取也不注入 |
| `memory_top_k` | 每轮注入几条记忆 | `8` | **0 = 不注入**（记忆仍然记录和展示，只是不参与回答） |
| `memory_token_budget` | 记忆 token 上限 | `600` | 整段的预算（含固定的开头说明），从「单轮上下文总预算」里划 |
| `memory_relevance_enabled` | 记忆按相关性排序 | `true` | 每轮拿当前问题给记忆做一次向量匹配，**只把最相关的几条**拼进提示词（见 12-b §B4）。代价是每轮多一次 embedding 调用；关掉就退回固定顺序排序，记忆照样注入 |

> ⚠️ **`memory_relevance_enabled` 关掉不影响记忆本身** —— 只是排序退回
> 「用户写的 > 管理员写的 > 自动抽的」。平台 `.env` 的 `MEMORY_RELEVANCE_ENABLED`
> 是总开关（两层都开才生效），租户改不了平台那一层。

**B1 摘要压缩的两个租户级配置项**（在通用配置页的「记忆」分类下）：

| key | 名称 | 默认 | 说明 |
| --- | ---- | ---- | ---- |
| `summary_enabled` | 开启会话摘要 | `true` | 关掉后长对话只剩「丢弃更早的轮次」，AI 会真的忘事。**开启会多一次 LLM 调用** |
| `summary_token_budget` | 摘要 token 上限 | `600` | 整段的预算（含固定说明，实测约 190 token），从「单轮上下文总预算」里划 |

> ⚠️ **`summary_token_budget` 填 200 可能一条都装不下** —— 摘要会**静默失效**
> （库里写好了，AI 从来没用过）。页面上把这句话写清楚了。
>
> ⚠️ **摘要的「抽取开关」跟记忆不一样**：记忆的抽取开关留在 `.env`
> （`MEMORY_ENABLED` 是平台成本边界），但摘要的开关给租户 ——
> 因为摘要是**每轮最多一次**的调用，长对话的租户几乎必然要开，
> 而成本敏感的租户可以用 `summary_enabled=false` 换回来。

> ⚠️ **`memory_token_budget` 算的是「整段」的预算**：记忆块有一段固定的开头说明
> （实测 124 token），填 200 可能一条都装不下。页面上把这句话写清楚了。
>
> ⚠️ **抽取的开关不在租户手里**：`MEMORY_ENABLED` / `MEMORY_MIN_CONFIDENCE` /
> `MEMORY_EXTRACT_TIMEOUT_MS` 留在 `.env` —— 抽取是**额外的一次 LLM 调用**，
> 「允不允许租户开着抽」是成本决策，该由平台统一控。租户能关的是「注不注入」。

**B2 重排序的租户级配置项**（在通用配置页的「**知识库**」分类下）：

| key | 名称 | 默认 | 说明 |
| --- | ---- | ---- | ---- |
| `rerank_enabled` | 开启重排序 | `true` | 关掉后走纯 RRF 排序（**不影响能不能召回**，只是排序退回融合算法）。**平台没配重排服务时这项无效** |

- 平台总开关在 `.env` 的 `RERANK_ENABLED`（硬边界：关掉时租户配的「开」也无效）
- **端点 / 凭据 / 模型不给租户**（`RERANK_API_URL` / `RERANK_API_KEY` / `RERANK_MODEL` 留在 `.env`）：
  重排服务是平台统一一套，租户只决定「用不用」
- ⚠️ **开了会多一次外部调用**：每轮检索多一次重排请求（网络 + 推理），
  排序通常更准但更慢、更贵。成本敏感的租户可以关掉
- ⚠️ **`.env` 的 `RERANK_API_URL` 留空 = 全平台不做重排**：配好地址即生效，
  不用再翻开关；没配地址时租户开关怎么设都没用

**B2 查询改写的租户级配置项**（在通用配置页的「**知识库**」分类下）：

| key | 名称 | 默认 | 说明 |
| --- | ---- | ---- | ---- |
| `query_rewrite_enabled` | 开启查询改写 | `false` | 把口语化的问题改写成更贴近知识库原文的检索词。**默认关闭** —— 每轮会多一次模型调用（多 1~3 秒 + 一份花费），而短问题（「年假几天」）改写基本没收益 |

- **默认关闭是有意的**：改写是**额外的一次 LLM 调用**，成本和延迟都要算在租户头上，
  而短问题的收益接近零 —— 「问法跟原文差很远」时收益才明显
- **改写失败一律回落原查询** —— 改写挂了就用用户原话去检索，不影响这一轮能答什么

**B6 多代理协作的租户级配置项**（在通用配置页的「**模型**」分类下）：

| key | 名称 | 默认 | 说明 |
| --- | ---- | ---- | ---- |
| `multi_agent_enabled` | 开启多代理协作 | `true` | 关掉后 AI 不再把子任务派给子代理，全部由主 agent 自己答 |

- ⚠️ **开了会多花一次 LLM 调用**（一次委派 = 一次非流式 `generateText`），
  token 成本是单代理的数倍 —— 成本敏感的租户可以关掉
- 委派出去的子任务**固定是三个内置角色**（订单 / 政策 / 优惠），租户改不了；
  子代理**只拿只读工具**（写操作留给主 agent 走 HITL 闸门）——
  见 [12-b](./12-b-需求-ai对话能力.md) §B6
- 实现见 `src/rag/query-rewrite.ts`，需求见 [12-b](./12-b-需求-ai对话能力.md) §B2

**B7 前台首页的两个租户级配置项**（在通用配置页的「**首页**」分类下）：

| key | 名称 | 默认 | 说明 |
| --- | ---- | ---- | ---- |
| `home_welcome_message` | 首页欢迎语 | `''`（空） | 显示在前台首页顶部。**留空则前端按租户名兜底**出一句默认文案，不会让首页变空白 |
| `home_suggested_questions` | 首页推荐问题 | `''`（空） | 首页「你可以这样问」的列表，**一行一个**，最多 8 条、每条 100 字。**留空则首页不显示这一块** |

- 这两项是 **string 类型**（通用配置页以前只有 number / boolean），
  字符串类型带了 `maxLength` 上限（欢迎语 200 字 / 推荐问题 2000 字）
- 「一行一条」的列表存的是**普通字符串**（换行分隔），后台渲染成多行输入框，
  保存时会**去掉空行和首尾空白**再存 —— 读取方（`GET /api/v1/customer/profile`）按换行拆开
- 生效链路：`GET /api/v1/customer/profile` → 前台首页 → **保存后立刻生效，不用重启**

**已知限制 / 注意事项**：

- ⚠️ **换 provider 仍然要改 `.env` 重启** —— 租户填的 base_url 能指向任意兼容
  Anthropic 协议的端点（包括自建网关），但 `.env` 里那些 provider 的凭据得先配齐
- ⚠️ **`CONFIG_ENCRYPTION_KEY` 配了就不能换**：换了对不上的旧密文解不开（会降级到平台
  默认凭据并在日志里告警，不会整个对话失败）
- ⚠️ **提示词缓存开关在智谱上实测不生效**：`cache_read_tokens` 仍是 0。
  智谱的 Anthropic 兼容端点把系统提示词映射到 `instructions` 字段，而 `cache_control`
  只对 `messages` 里的 content block 有意义。原生 Anthropic 端点上应该可用（未实测）
