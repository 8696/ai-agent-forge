# 01 · 需求与场景

## 1.1 一句话目标

**做 AgentForge —— 一个多租户的 AI Agent 平台**。当前首个能力是文档问答：

- 后台管理员上传文档（PDF / Markdown / TXT）
- 系统拆块 + Embedding 入向量库
- 前台用户通过对话向 AI 查询文档里的知识

> 未来要加的能力：工具调用（外部业务系统）/ 多代理协作 / 工作流 + 人工审批 / 多渠道接入（邮件 / 微信）等。任何不超出 §1.5 Out of Scope 的新功能都可以叠加。

三步流程：

```
后台管理员
  上传 .md / .txt / .pdf  →  系统拆块 → 存数据库 + Embedding → 入向量库
                                                              ↓
前台用户  ─── 跟 AI 聊天 ───  AI 检索向量库  ────  返回引用了文档片段的回答
```

> **不做什么**（详 §1.5）：查订单 / 改地址 / 退款 / 开 ticket 这些需要**真实外部业务系统**的功能，
> 本项目不接（要接得另起一个业务系统项目，通过工具接入 —— 现在 `mcp` 不做，
> `http` 工具只是本地 mock）。
> ⚠️ 但**平台侧的工具调用链路本身已经跑通**（B3 + B5 · 2026-10-25/26）：
> 这四类场景都有内置 mock 工具（`query_order_status` / `update_shipping_address` /
> `submit_refund_request` / `create_after_sale_ticket`），AI 会真的调它们、按闸门走审批。
> 差的是「接到真的业务系统」那一步。

## 1.2 用户角色（3 层登录）

> 系统有 3 层身份，**每一层登录入口不同、用途不同**。SaaS 平台方 → 租户后台管理员 → 前台用户，**只能往下授权**。

| 层                          | 谁有这种身份                                   | 登录入口                                        | 账号字段                                           | 用途                          |
| --------------------------- | ---------------------------------------------- | ----------------------------------------------- | -------------------------------------------------- | ----------------------------- |
| **SaaS 平台方**（system）   | 卖这个系统的产品方（系统的「你」）             | `/system/login`（UI 可选；默认建议 SQL 手工建） | 邮箱 + 密码（**不要租户号**）                      | 创建租户、给租户初始化管理员  |
| **租户后台管理员**（admin） | 每个租户一个，由 SaaS 平台方建租户时自动初始化 | `/admin/login`                                  | 邮箱 + 密码 + **租户号**（必填）                   | 管知识库 / 工具 / 配置 / 用户 |
| **前台用户**（customer）    | 由租户后台 admin 创建                          | `/customer/login` 或匿名 `/widget/:tenantCode`  | 邮箱 + 密码 + **租户号**（**可选**，URL 里已经有） | 跟 AI 聊天、问问题、看历史    |

> **租户号必填的原因**：邮箱**不跨租户唯一**（两家公司都有 `zhang.san@xxx.com`）。后端登录验证用 `WHERE email = ? AND tenant_id = (SELECT id FROM tenants WHERE code = ?)`，**不填租户号查不出来是哪个租户**。

> **轻权限原则**：整个系统就这 3 层，不做「权限矩阵」「角色继承」「菜单权限」之类。

## 1.3 SaaS 平台方 → 创建租户 → 初始化管理员的标准流程

```
[SaaS 平台方] 打开 /system/login（如果有的话；或者 SQL 手工建）
        │
        ▼
  POST /api/v1/system/tenants（创建租户）
    输入：租户号（code）/ 租户名 / 初始管理员邮箱 / 初始管理员密码
        │
        ▼
  系统自动做三件事：
    1. INSERT INTO tenants (id, code, name, ...)   ← 租户号必须全局唯一
    2. INSERT INTO users (id, tenant_id, role='admin', email, password_hash)
                                    ↑ 第一个 admin 账号，密码强制首次登录改
    3. INSERT INTO settings 给租户默认配置（prompt / model / 限额）
        │
        ▼
  返回租户记录 + 初始管理员账号
        │
        ▼
[SaaS 平台方] 把「租户号 + 初始管理员邮箱 + 密码」告诉租户
        │
        ▼
[租户后台管理员] 打开 /admin/login
  输入：邮箱 + 密码 + 租户号
  登录成功 → 强制改密码
        │
        ▼
  进入后台 → 上传文档 / 配置提示词 / 创建前台用户
```

## 1.4 要在演示里跑通的 5 条用户故事

1. **客户问退款**：RAG 检索退款政策 + 调用订单查询工具查到具体订单 + 给出退款步骤
2. **客户要改地址**：多代理协作（监督者 → 客服分析 → 操作调改单 → 审核等用户确认 → 完成）
3. **员工问年假**：直接 RAG 检索政策文档，引用原文片段回答
4. **客服批量处理 ticket**：Agent 循环处理 50 条 ticket，每一条都有独立 trace
5. **管理员看成本异常**：观测面板定位到具体用户 + 具体场景的 token 暴涨，修复 prompt 或加缓存

## 1.5 不做（Out of Scope）

- 不做支付集成（用第三方支付）
- 不做电话客服 / 视频客服（只做文字）
- 不做复杂 CRM（只接已有系统的工具）
- 不做原生移动 App（响应式 Web）
- 不部署到任何云（本地运行，通过 localhost 访问）
- 不做复杂角色权限矩阵（3 个角色够用）
- **不做「转人工」/ 人工转接 / 工单流转**（2026-10-25 明确移出需求）：
  本系统没有「客服坐席」这个角色（[05-a §5.1](./05-a-数据模型-mysql.md) 说明了
  `agent` 角色只是历史 ENUM 留位，代码层面拒收它登录），
  也没有「AI 答不上来」的判定机制（没有置信度、没有检索为空就拒答的闸门）。
  没有坐席就没有转接对象 —— 「转人工」在本产品里只能是「一个租户自己配的联系方式字符串」，
  不是一项功能。⚠️ `sessions.status` 的 `'transferred'` 枚举值**保留**
  （将来真做工单流转时用得上），但它现在全库无人写入或读取
- **不做 Word（.docx）解析**（2026-10-25 移出需求）：上传格式只有
  PDF / Markdown / TXT。库里的 `documents.file_type` ENUM 也去掉了 `'word'`
  （迁移 `021-alter-documents-file-type`）。**这是有意的决定，不是待办**
  （裁定表见 [12-e](./12-e-需求-业务接入与平台运营.md) 表 3）

## 1.7 非功能需求

| 维度           | 指标                   | 说明                                           |
| -------------- | ---------------------- | ---------------------------------------------- |
| **延迟**       | p95 ≤ 3 秒             | 从用户消息到开始看到回复的时间                 |
| **可用性**     | 99.5%                  | 月度统计                                       |
| **错误率**     | ≤ 1%                   | 5xx 错误占总请求的比例                         |
| **成本**       | 单条 ≤ $0.05           | 1000 DAU 月费 ~$3901（仅 LLM + Embedding API） |
| **并发**       | ≥ 30 req/s             | 单机可扛（开发机 + Docker Compose）            |
| **可观测**     | 100% 请求有 trace      | 不能有静默失败                                 |
| **可维护**     | 模块化 + 文档化        | 每个模块独立可替换                             |
| **安全合规**   | 注入检测 + 脱敏 + 审计 | 用户数据全程可追溯                             |
| **多租户隔离** | 严格                   | 任何查询不能跨租户                             |

> ⚠️ **这张表里是「目标（SLO）」，后台告警条用的是另一套阈值** ——
> 别把 p95 ≤ 3 秒当成「超过 3 秒就会告警」。告警阈值**更宽、而且按租户可配**
> （在 `/admin/settings` 的「成本」分类里改，**填 0 = 不看该项**），
> 配置项是 `alert_p95_latency_ms` / `alert_error_rate` / `alert_single_cost_usd`。
>
> | 维度     | 本表的目标（SLO） | 后台告警阈值默认值 | 说明                                       |
> | -------- | ----------------- | ------------------ | ------------------------------------------ |
> | 延迟     | p95 ≤ 3 秒        | p95 > **5000 ms**  | 5 秒是「明显不对劲」的线，不是「违反目标」   |
> | 错误率   | ≤ 1%              | > **0.05**（5%）   | 同上 —— 比 SLO 宽 5 倍                      |
> | 单条成本 | 单条 ≤ $0.05      | > **$0.5**         | 同上                                        |
>
> ⚠️ 告警的统计窗口是**「今天」**（不是滚动 5 分钟）；
> 「客户端断开」**不算错误**（否则用户自己关页面会把错误率刷高）。
> 详见 [12-d §D2](./12-d-需求-运维稳定.md)。

## 1.9 关键用户路径（5 条）

路径 1 · 前台用户 → Agent（文档问答场景）

```
打开电商网站 → 点右下角挂件 → 输入「我上周买的 X 怎么退款？」
→ Agent 调 RAG 查政策 + 调订单 API → 返回退款步骤
```

路径 2 · 前台用户 → 改地址

```
客户要改收货地址 → 监督者分析 → 客服代理理解意图
→ 操作代理调改单接口 → 审核代理等用户确认 → 完成
```

路径 3 · 前台用户 → 自助查询

```
员工登录 → 输入「年假怎么算？」
→ RAG 检索政策文档 → 引用原文片段回答
```

路径 4 · 后台用户（agent） → 批量处理

```
客服登录 → 「帮我把这 50 条 ticket 都分类」
→ Agent 循环处理 → 每条独立 trace → 完成后列表展示
```

路径 5 · 租户管理员 → 配置 + 监控

```
管理员登录 → 上传文档 → 等待索引 → 输入测试问句看命中
→ 看 Trace 详情定位问题 → 改 prompt → 看评测分数变化
```

## 1.10 风险与边界

| 风险             | 缓解                                 |
| ---------------- | ------------------------------------ |
| LLM API 挂了     | 主备切换（改 base URL）+ 限流 + 重试 |
| 成本失控         | 监控 + 告警 + 缓存 + 配额            |
| 提示词注入       | 检测 + 直接拒绝                     |
| 检索召回率低     | 混合检索 + 重排序                    |
| 多代理上下文超长 | 短期记忆只保留最近 N 轮              |
| 敏感操作被滥用   | 审核代理 + 人工确认                  |
