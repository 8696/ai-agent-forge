## E · 业务接入

### E1 · 网页挂件 + REST API ✅ 已落地 2026-10-24

**需求**：前台用户通过聊天挂件跟 AI 聊；外部系统通过 REST API 调用。

**当前状态**：**两半都做完了**。新增第 4 个子系统 `public/`（`/api/v1/public/*`），
跟 system / admin / customer 并列但**鉴权命名空间完全独立**。

**使用技术**：

- 前端：Vite + React 18 + AntD + SSE 客户端
- 后端：Koa + SSE（流式响应）
- 公开聊天挂件：无需登录
- 对外 API：API Key（`ak_<nanoid(32)>`）

**接口**（`src/gateway/public/`，前缀 `/api/v1/public`）：

| 方法   | 路径                                              | 鉴权             | 说明                                   |
| ------ | ------------------------------------------------- | ---------------- | -------------------------------------- |
| GET    | `/widget/:tenantCode/info`                       | 无               | 按 URL 里的 tenantCode 返回租户名     |
| POST   | `/widget/:tenantCode/sessions`                   | 无               | 建匿名会话，返回 `session_id` + token  |
| GET    | `/widget/:tenantCode/session`                    | 匿名 token       | 恢复历史（关浏览器再打开还在）         |
| POST   | `/widget/:tenantCode/messages`                   | 匿名 token       | SSE 流式对话                           |
| POST   | `/widget/:tenantCode/tool-approvals`             | 匿名 token       | 确认执行敏感工具（B3 的 HITL）         |
| POST   | `/widget/:tenantCode/tool-approvals/reject`      | 匿名 token       | 取消执行敏感工具（B3 的 HITL）         |
| GET    | `/search`                                        | API Key（read+） | 知识库检索（**不调 LLM、不花钱、不留会话**） |
| POST   | `/chat`                                          | API Key（write+）| 一次性 JSON 回答 + 引用                |
| POST   | `/chat/stream`                                   | API Key（write+）| SSE 流式回答                           |

> ⚠️ **挂件的全部端点都带 `:tenantCode`**（`/widget/:tenantCode/xxx`）——
> 租户号在路径里，不是 query。挂件侧**没有登录态**，但会话是**匿名 token 认领**来的，
> 所以「敏感工具确认 / 取消」照样能调（`X-Widget-Token` 头认领会话）。

**对外 API 的字段级能力**（`src/gateway/public/api-routes.ts`）：

- **多轮续会话**：`/chat` 与 `/chat/stream` 的请求体可带 `session_id`
  —— 必须是这把 key 所属租户下的 `channel='api'` 会话，否则 404；**不传就新开一段**
- **思考模式开关**：请求体可带 `thinking`（布尔）——
  只能把思考**打开**；租户配了 `thinking_budget_tokens` 的话一直生效
- **`/chat` 的响应体**：`answer` + `citations` + `session_id` 之外，还带
  `message_id`（本轮 assistant 消息 id）/ `moderation`（审核结论）/
  `tool_calls`（B3 的工具调用记录 —— 外部系统能知道 AI 调了哪些工具、结果是什么）
- **`/search` 的响应体**：命中片段之外还带 `took_ms`（检索耗时）+
  `sources`（含 `doc_id` / `chunk_index` / `source`）
- **按 API Key 的限流桶**：限流维度是 `apikey:<key id>`（一把 key 一个额度），
  **跟租户额度叠加生效**

**API Key 管理**（`src/gateway/public/api-key-admin-routes.ts`，前缀 `/api/v1/admin/api-keys`，
**admin JWT 鉴权** —— 管理端点属于 admin 命名空间）：

| 方法   | 路径       | 说明                                             |
| ------ | ---------- | ------------------------------------------------ |
| GET    | `/`        | 列表（**永远不返回 hash / 完整 key**）           |
| POST   | `/`        | 新建 → 完整 key **只在这一次的响应里出现**       |
| PATCH  | `/:id`     | 改权限分级（scope）—— **立刻生效**（清鉴权缓存） |
| DELETE | `/:id`     | 撤销（软删除 + 立刻清掉鉴权缓存）                |

**字段补充**：

- **新建时可传 `expires_at`**（ISO8601，到期时间）—— 不传 = 永不过期
- **列表额外返回三个时间戳**：`last_used_at`（最后一次被调用）/
  `expires_at`（到期时间）/ `revoked_at`（撤销时间）；
  `PATCH /:id` 的请求体**只接受 `scope`** —— 这三个时间戳没有对应的改动端点

**页面**：`/widget/:tenantCode`（公开挂件）、`/admin/api-keys`（租户后台管自己的 key）

**两个设计决策**（论证见对应源文件顶部注释）：

- **匿名会话用签名 token，不用裸 session id** —— 凭证形如 `w1.<session_id>.<HMAC-SHA256 签名>`，
  走 `X-Widget-Token` 头（**不进 URL**）。裸 id 一旦泄露（会进 nginx 访问日志 / Referer / 截图）
  任何人都能读走整段对话；签名 token 把「知道 id」和「持有凭证」分成两件事。
  选它而不是「另发随机 token 存库」，是因为后者要么加表要么加列，
  而 `sessions.metadata` 是 JSON 走不了索引，每次请求全表扫 sessions
- **API Key 定位是「prefix 粗筛 → bcrypt 逐个比」** —— bcrypt 单次 200~300ms，
  外面套了一层进程内缓存（TTL 60s）；后台撤销走 `invalidateApiKeyById` 主动清缓存，
  所以「点撤销」是立即生效的

**验收**：

- ✅ 打开公开挂件页面 → 问个问题 → 流式逐字显示 AI 回答
- ✅ 关闭浏览器 → 再打开 → 历史还在（靠 localStorage 里的 token 恢复）
- ✅ 拿 API Key 调 `/api/v1/public/chat` → 拿到 `answer` + `citations` + `session_id`
- ✅ 鉴权命名空间隔离：customer 的 JWT 打过来 401；API Key 打 customer 端点也 401；
  挂件的匿名 token 不能当 API Key 用，反之亦然
- ✅ 后台 `/admin/api-keys` 能新建（完整 key 只显示一次）/ 列表 / 撤销
- ✅ **API Key 权限分级**（2026-10-25 补）：`read` 级的 key 能查知识库、
  发起对话被挡（**403**，不是 401）；`write` 级的能发起对话；
  改权限立刻生效（集成测试 `tests/integration/api-key-scope.test.ts`，8 个用例）

**已知边界**：

- **挂件和对外 API 的会话没有清理机制** —— 匿名会话永远留在 `sessions` 表里
- **匿名场景限流挡不住「一个人开十个浏览器」** —— 匿名没有身份可限
- **`api_keys.key_prefix` 只有 8 位，单独按 prefix 查走不了索引** → 全表扫，key 一多会慢。
  正解是加一列 sha256 确定性哈希
- **API Key 的 `admin` scope 前端可选、但没有对应端点** ——
  `scope` 枚举含 `admin`（代码注释里写的是「预留」），但对外 API
  **没有任何 admin 专属端点**（`src/gateway/public/api-routes.ts` 里自述「预留」）。
  ⚠️ 后台 `/admin/api-keys` 的下拉框里「管理员」这一档**是可以选的**
  （`web/pages/admin/ApiKeysPage.tsx`）→ 用户能建出一把**看着比 `write` 大、
  实际能力等价于 `write`** 的钥匙
- 挂件页没有 👍👎（匿名反馈没地方存）；对外 API 的 SSE 返回的是 AI SDK 的 UI message stream 格式，
  外部系统得按这个协议解析

### 平台方自己的登录与跨租户读侧（平台方基础设施，不占 F 类编号）

**需求**：平台方有**独立的一套账号**（`system_users` 表，**不挂任何租户**）。
除了管租户（F1 / F2），平台方还要能登录、能改自己的密码、
能看**跨租户**的审计和总览数字。

**接口**（`src/gateway/system/`，前缀 `/api/v1/system`）：

| 方法   | 路径               | 说明                                                                  |
| ------ | ------------------ | --------------------------------------------------------------------- |
| POST   | `/login`           | 平台方登录（邮箱 + 密码，**不要租户号**）                             |
| GET    | `/me`              | 当前平台方身份（闸门 `requireSystemUser`）                            |
| POST   | `/change-password` | 改自己的密码                                                          |
| GET    | `/audit`           | **跨租户**审计日志 —— **含系统级日志**（`tenant_id` 为空那些）        |
| GET    | `/audit/actions`   | 真实的 action 清单                                                    |
| GET    | `/stats`           | 平台方总览 KPI —— **唯一返回跨租户数字的端点**，闸门 `requireSystemUser` |

**页面**：`/system/audit`（平台方跨租户审计）

> ⚠️ **租户 admin 那条路看不到系统级日志** ——
> `GET /api/v1/admin/audit` 只看得到**本租户**的日志（`tenant_id` 为空的系统级日志租户 admin 看不到）。

### F1 · System 端管理租户列表 + 重置租户 admin 密码 ✅ 已落地（2026-10-13 · 租户列表 2026-10-26）

**需求**：SaaS 平台方（system user）能列出所有租户、看每个租户的基本信息，并能重置每个租户初始 admin 账号的密码（admin 账号是 system 在建租户时自动创建的）。

**租户列表与详情**（`src/gateway/system/tenant-routes.ts`）：

- **列表走服务端筛选**：`GET /tenants?keyword=&plan=&status=`
  —— `keyword` 搜租户号**或**名称、`plan` 筛套餐（free / pro / enterprise）、
  `status` 筛 `active` / `disabled` / `expired`
  ⚠️ **「已到期」是算出来的**，不是 `tenants.status` 上的枚举值：
  `expires_at <= 现在` 的租户在列表里单独标 `expired: true`，
  跟「被禁用」是**两回事**
- **列表每行额外返回**：`user_count`（该租户用户总数）/
  `admin.must_change_password`（租户 admin 是否还欠一次强制改密）
- **租户详情**：`GET /tenants/:id` 带 4 项统计 ——
  `user_count` / `session_count` / `document_count` / `total_cost_usd`（累计花费，估算值）。
  全部按 `tenant_id` 过滤 —— 平台方看的是**单个租户**的数，不是全平台的

**验收**：

- 列出所有租户，每条带 admin email
- 改 name / plan 成功更新
- 重置租户 admin 密码 → admin password_hash 更新 + must_change_password=true
- 跨子系统防御：admin token 调 system 端点 → 401

### F2 · 平台方：修改租户到期时间 + 禁用 / 启用租户 ✅ 已落地（2026-10-13 · 端到端用例 2026-10-26）

**需求**：SaaS 平台方（system user）能改租户的到期时间（`expires_at`，NULL = 永不过期），也能禁用 / 启用租户。被禁用的租户、或已到期的租户，在登录端点都返回 401（**统一响应与「邮箱或密码错误」完全一致的 401**，不区分禁用 / 到期 / 密码错，防账号枚举 + 防泄漏租户内部状态）。

**使用技术**：

- MySQL `tenants` 表加 `expires_at` + `status`
- Koa 路由：2 个子资源 PATCH 端点（与 F1 同文件、分桶）
- Zod 校验 + Audit Logs
- 登录拦截：登录端点在校验租户后**多走一道**租户状态闸门，**但只有两处共用一个函数**：
  - **admin + customer 复用 `src/lib/tenant-gate.ts` 的 `assertTenantAccessible`**
    → 抛 **401「邮箱或密码错误」**（与密码错的响应体**逐字段完全一致**）
  - **挂件 + 对外 API 各自内联了同逻辑**，**没有复用那个函数**
    → 抛 **403 `TENANT_UNAVAILABLE`**，文案也不同
    （挂件「该客服暂未提供服务」/ 对外 API「该租户的服务已暂停」）
    —— 匿名侧**没有「密码错」可以对齐**，所以不共用
- 防御自锁：禁用的「系统初始租户」拒绝 PATCH `status=disabled`
- 跨子系统防御：复用 `requireSystemUser`

> ⚠️ **「系统初始租户」是什么**（2026-10-25 说清楚）：
> 本项目**没有**平台方自带的初始租户 —— 平台方账号在 `system_users` 表，
> **不挂任何租户**，所以「把租户全禁掉」不会让平台方进不去（没有自锁风险）。
>
> 但租户号 `system` 是**合法**租户号（`^[a-z0-9-]+$`）：平台方自己建一个
> 号叫 `system` 的租户（平台自用），禁掉它就等于把平台自己停掉了 ——
> 所以这条防御拦的是**这种租户**。
>
> ⚠️ 换句话说：**这条防御是有前提才生效的** —— 前提（存在 code='system' 的租户）
> 不成立时它就是一段惰性代码。验收测试里把前提造出来验证它（`tests/integration/f2-tenant-lifecycle.test.ts`）。

**验收**：

- 改到期时间（ISO8601）→ tenants.expires_at 更新；audit_logs 写一条 TENANT_EXPIRES_CHANGE
- 改到期时间为 null → 清空到期时间（永不过期）
- 改 status 为 disabled → tenants.status 改为 disabled；audit_logs 写一条 TENANT_STATUS_CHANGE
- 禁用租户后，登录端点 → 401「邮箱或密码错误」（与密码错的响应体**逐字段完全一致**）
- 到期租户登录 → 401「邮箱或密码错误」（同上，统一）
- 改回 `active` + 清空到期 → 立即可登录（不需要重启服务）
- 跨子系统防御：admin token 调 system 端点 → 401
- 防自锁：禁用 `code='system'` 的初始租户 → 400「不能禁用系统初始租户」
- 列表返回值带 `status` + `expires_at` 字段

> ✅ **2026-10-25 补齐了三条之前没被测试锁住的验收**（`tests/integration/f2-tenant-lifecycle.test.ts`）：
>   - 「禁用 / 到期的响应体与密码错**逐字段完全一致**」—— 以前只断言了 401，
>     哪天有人给禁用态换个文案，测试不会红
>   - 「防自锁 → 400」—— 以前这条**永远触发不到**（没人建 code='system' 的租户），
>     现在测试把前提造出来验证它
>   - 「审计日志写两条 action」—— 以前没有测试覆盖

**平台方写操作的审计**（2026-10-26 补齐）：

平台方在本系统里的**全部写操作都留审计**（`audit_logs`）：

| action                        | 触发端点                                                    |
| ----------------------------- | ----------------------------------------------------------- |
| `TENANT_CREATED`              | `POST /api/v1/system/tenants`                               |
| `TENANT_UPDATED`              | `PATCH /api/v1/system/tenants/:id`（改 name / plan）        |
| `TENANT_ADMIN_PASSWORD_RESET` | `POST /api/v1/system/tenants/:id/admin/reset-password`      |
| `TENANT_EXPIRES_CHANGE`       | `PATCH /api/v1/system/tenants/:id/expires_at`               |
| `TENANT_STATUS_CHANGE`        | `PATCH /api/v1/system/tenants/:id/status`                   |

> ⚠️ 2026-10-26 之前，前三个写操作**一条审计都没写**
> （只有「改到期 / 改启停」两处写了 `writeAuditLog`）——
> 平台方建租户 / 改租户 / 重置租户 admin 密码**在审计日志里查不到**。
