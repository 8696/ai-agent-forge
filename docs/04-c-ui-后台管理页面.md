- 实现：`web/pages/admin/KnowledgeDocumentsPage.tsx`，数据来自 `GET /api/v1/admin/knowledge`
- **上传格式只支持 PDF / Markdown / TXT**。
  前端 `accept` + 后端扩展名校验双重拦截，非法扩展名返 400
- **上传是同步的**：后端在同一个请求里跑完「解析 → 拆块 → Embedding → 入库」，

- 状态：`uploaded` → `indexing` → `ready` / `failed`；失败行显示红色「索引失败」，

- 4 张统计卡：「已索引块数」= 本租户 ready 文档的块数合计；
  「关键词索引块数」= BM25 内存索引，**服务重启后重建期间会偏低**，卡片上会挂一个「重建中」提示；
  「向量库总点数」是**跨租户**的，仅供运维参考
- 搜索 + 状态筛选 + 分页都在**服务端**做（`?page=&page_size=&keyword=&status=`）

```
└──────────────────────────────────────────────────┘
```

- 实现：`web/pages/admin/KnowledgeSearchPage.tsx`，调 `POST /api/v1/admin/knowledge/search`
- 输问句 → 混合召回 + RRF 融合（+ 重排）→ 显示命中块；右上角显示本次耗时（ms）
- **这一页不调 LLM、不生成 AI 回答**。它的价值就是看清「哪些块被召回了、为什么」，
  加了 LLM 反而掩盖了检索层的问题。要看回答效果去前台聊天页
- 每条命中显示：文档名 + 块序号 + `相关度` + `语义第 N` / `关键词第 N` 两个排名标签 + 片段预览（可展开全文）
- 每条左侧有绿色/灰色竖条：绿色 = 两路都召回（说明向量和关键词都认为它相关）
- 空结果时提示「检查知识库是否有已就绪的文档，或换个说法再试」

> **重排痕迹（B2 重排序 · 2026-10-25）**：
>
> - 结果区右上角一个 `已重排` / `未重排` 标签 —— `未重排` 有三种可能：
>   平台没配重排服务、租户在「租户设置 → 知识库」里关掉了、调用失败已自动降级。
>   标签的 tooltip 里写了这三种可能，鼠标悬停能看清
> - 每条命中多一个 `重排 x.xxx` 标签（紫色）—— 重排模型给的原始分
> - `语义第 N` / `关键词第 N` 仍然是**重排之前**的排名：两者对不上恰恰说明重排改了顺序

> **score 怎么读**（`src/rag/hybrid-search.ts` 有完整推导）：
>
> - **重排生效时** `hits[].score` 是**重排分**（模型给的原始分，落在 [0,1] 时原样用，
>   超出范围按批次 min-max 归一化）；**降级 / 未启用时**才是下面的归一化 RRF 分
> - 降级时的 `hits[].score` 是**归一化到 [0,1]** 的 RRF 分：`1.0` = 向量 + 关键词两路都排第一；
>   只有一路排第一最高只能到 `0.5`。**这是设计如此，不是 bug** ——
>   归一化用的是「双路都第一」的理论满分 `2/(k+1)`，不是「本次最高分」。
>   早期设计稿里写的「按本次最高分归一化」会让任何一次检索的第一名都显示成 1.00，哪怕语料里根本没有相关文档。
> - `hits[].rrf_score` 是原始 RRF 分（k=60，单源最大 ~0.0164，双源最大 ~0.0328），**别拿它画进度条**，会被压成全 0
> - `hits[].rerank_score` 是重排原始分（没重排时为 `null`）
> - `sources: ['vector' | 'bm25']` + `vector_rank` / `bm25_rank` 才是解释「为什么命中」的关键，比分数本身有用
> - **早期的 `score_threshold`「阈值」交互已废弃**：RRF 分没有可解释的阈值语义，
>   后端不再接收该字段。要做「只看前 N 条」用 `top_k` 即可

### 5.4 模型 & 提示词

#### 5.4 模型 & 提示词

> **拆成三页**（2026-10-21 落地）：不同形态的配置用不同页面 + 不同存储。
> 混在一页的后果是「东西一多就不知道该往哪放」。

| 页面                       | 承接什么                     | 存储               |
| -------------------------- | ---------------------------- | ------------------ |
| `/admin/models`            | 模型列表（多条 + 启用切换）  | `tenant_models`    |
| `/admin/prompts`           | 提示词多版本                 | `prompt_versions`  |
| `/admin/settings`          | 通用配置 KV                  | `tenant_settings`  |

##### 5.4.1 模型选择 `/admin/models`（C4）

AntD Table + 抽屉表单。列：名称（带「用途」+「启用中」标记）/ 模型 id / Base URL / API Key /
采样 / 操作（启用 · 试连 · 编辑 · 删除）。

- **一条模型 = 一套完整连接配置**（名称 / provider / 模型 id / Base URL / apiKey /
  Temperature / Max Output Tokens / 提示词缓存），互不共享
- **「用途」字段**（`usage_scope`）：`对话` / `记忆抽取` / `会话摘要`
  - 对话走 `chat` 那条；**记忆抽取走 `memory` 那条**；**会话摘要走 `summary` 那条**
  - 没单独配 `memory` / `summary` 模型时，它们回落到对话模型（不配也能用，行为跟以前一样）
  - 单独配的意义：这两条都是**独立的一次 LLM 调用**，推理型模型的思考 token 全额算
    输出 token（实测一次 2000+），租户可以用一条便宜模型压这项成本
- 「新建模型」抽屉；编辑时**留空 API Key = 保持原样**（不重填也能改别的字段）
- 每条独立「试连」按钮（真发一次最小请求，不落消息表）
- **每个用途各自一条启用项**（切换在单事务里保证「每租户每 scope 恰一条启用」，
  三个 scope 互不影响）；某个 scope 的第一条模型自动成为该 scope 的启用项
- 顶部横幅常驻显示**三条**当前生效模型：「对话走哪条」+「记忆抽取走哪条」+
  「会话摘要走哪条」，没有启用项时提示走平台默认 / 跟随对话模型

> **与原规格的差异**：「备用模型下拉」做成「模型列表 + 启用切换」——
> 多条模型比一个下拉更直观，而且能表达「自建网关 + 官方 API 并存」。
> 「Max Tokens」改成 Max **Output** Tokens（默认 2048，对齐 LLM 输出上限语义）。
>
> ⚠️ **2026-10-26 补**：上面的「与原规格的差异」只说了**一半** ——
> 「备用模型下拉」这个字段**加回来了**（模型编辑抽屉里一个下拉，候选 = 同用途、且不是自己）。
> 两种并存：**列表管「手动切」，备用下拉管「自动切」**
> （主模型调用失败时自动顶上，只在还没吐过内容时才切）。
> 见 [12-c §C4](./12-c-需求-管理员可配置.md)。

### 5.6 评测 ✅ 已落地 2026-10-24

#### 5.6.1 评测集 `/admin/evaluation/datasets`（P6）

- 列表：name / version / 题目条数 / 跑过次数 / 最近总分 / 创建时间
- 「新建评测集」按钮：弹窗填名称 + 版本 + **JSONL 原文**
  （也支持「从文件读入 JSONL」—— 读文件内容填进文本框，不走后端上传）
- **坏行会被跳过**：每行单独解析，坏行记进 `skipped` 数组返回，前端提示「N 行被跳过」。
  一行格式不对不该让整份 200 条的评测集传不上去
- 单击：抽屉显示题目预览（题目 / 参考答案 / 场景 / 难度）
- 行内操作：查看 · **跑评测** · 删除

#### 5.6.2 评测结果 `/admin/evaluation/runs`（P7）

- 趋势图（ECharts 折线）：4 维分数（accuracy / completeness / style / safety）
- 列表：每次跑的结果（时间 / 提示词版本 / 模型 / 状态 / 四维分数 / 总分 / 成本）
- 状态：跑批中显示**进度环**（`已完成/总数`）；跑批在后台跑，页面 5 秒轮询一次
- 单击：抽屉显示 4 维分数 + **程序侧指标**（p95 延迟 / 单条最高成本 / 花费）
  + 每条 case 的得分和**大模型裁判理由**

> **与原规格的差异**：
> - 跑批是**后台异步**的（接口返 202 + run id），不是同步跑完再返回 ——
>   50 题 = 100 次 LLM 调用，同步跑 HTTP 必超时
> - 「上传评测集」做成了**粘贴 / 读文件填文本框**，不是 multipart 上传 ——
>   评测集是 JSONL 文本，前端读进文本框后再提交，后端只收一种格式，解析逻辑只有一份

- **左栏**：有记忆的用户列表（邮箱 + 记忆条数），点击切换右栏；窄屏（< md）折到上方一整行
- **右栏**：选中用户的记忆表格 —— 内容 / 分类 / 来源 / 置信度 / 被引用次数 / 更新时间 / 操作
- **筛选**：分类、来源、状态（生效中 / 已归档 / 全部）、内容关键词
- **操作**：
  - 「编辑」→ 抽屉改内容 + 分类（改完下一轮对话立即生效）
  - 「归档」→ 软删（`status='archived'`），用户自己也能恢复；管理员另有物理删除（合规清理）
  - 「添加记忆」→ 管理员给选中的用户打标（`source='admin'`）。
    典型场景：客服接到电话后记一笔「这个客户只关心物流时效」——
    这种线下才知道的信息自动抽取抓不到
- **来源标签**：`自动抽取` / `用户自写` / `管理员` —— 一眼看出这条记忆是谁写的
- **分类配色**：画像紫 / 偏好蓝 / 事实绿 / 情境橙（跟前台「我的记忆」页一致）
