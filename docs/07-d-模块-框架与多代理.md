### 模块 13 · Agent 框架对比

**解决什么问题**：手写循环能跑通，但项目大了需要框架的工程能力（状态持久化、断点恢复、可观测性）。

**用到的技术**：

- LangGraph：用图描述代理流程
- 状态持久化、内置 HITL、可视化

**选型**：手写循环为生产主用，LangGraph 用于复杂工作流场景。

> ⚠️ 原始设计稿里写的「对比文档写在 `/docs/wiki/framework-comparison.md`」**没有兑现** ——
> 定了「不对比框架」之后就没产出过这份文档（`docs/wiki/` 目录不存在）。
>
> **本节下面就是那份「对比」的最终形态** —— 不是框架对框架的横向对比，
> 而是**「本项目的需求池到底需不需要『图』这个形状」**的判定。
> 判定标准、逐条结论、成本分析、翻案信号全在这里 —— **这是本项目关于
> LangGraph 的唯一权威落点**，别处（12-b / 12-e / AGENTS.md）只引用，不重复论证。

#### 13.1 · 本项目实际做法

用 **Vercel AI SDK** 作为 Agent 框架（提供 `streamText` / `tool()` / 自动循环）。
**不**用 LangGraph、不对比其他框架。详见 `07-b-模块-工具与agent.md` 模块 07。

---

#### 13.2 · 需求池逐条判定（2026-10-26 · 全量评估）

**问的是「这条需求需不需要『图』这个形状」，不是「LangGraph 好不好」。**

LangGraph 提供的其实是五样东西：`StateGraph`（节点 + 边）/ checkpointing（断点恢复）/
`interrupt()`（HITL 暂停）/ 条件边 / 并行 fan-out 与多代理 handoff。

**判定标准**：一条需求如果**没有分支、没有回退、没有多个角色、没有运行时可变的拓扑**，
它就不需要图 —— 普通函数 + 状态表就够，而且更省事。

| 需求 | 要图吗 | 理由 |
| ---- | ------ | ---- |
| A1–A4 多租户 / 登录 | ❌ | 隔离过滤 + CRUD + JWT，没有多步编排 |
| B1 / B1.1 多轮对话 / 摘要 | ❌ | 上下文窗口管理，一次调用一件事 |
| B2 RAG 检索 | ❌ | 一次召回 + 排序，不是流程 |
| B3 工具调用 | ❌ | 单层循环（`stopWhen: stepCountIs(5)`），无分支无回退 |
| B4 记忆 | ❌ | 抽取 + 注入，单步 |
| **B5 状态机工作流** | ⚠️ | **图形状，但已用手写做完了**（§13.4） |
| **B6 多代理协作** | ✅ | **唯一真正的 LangGraph 场景**（§13.5） |
| B7 前台首页 / C1–C4 管理员可配置 | ❌ | 纯 CRUD + KV |
| D1–D6 评测 / 观测 / 成本 / 安全 / 可靠性 / 测试基建 | ❌ | 横切关注点，不是编排 |
| E1 挂件与对外 API / E2 租户配置 / F1–F2 平台方运营 | ❌ | CRUD + 鉴权 |

**结论：24 条需求里 22 条跟「图」无关。**

需求池的主体是 **CRUD + 检索 + 鉴权 + 观测**，不是编排 —— 这才是「用不上 LangGraph」
的真正原因。**不是「用不上这个框架」，是「用不上『图』这种抽象」。**

⚠️ **B3 值得单说**：很多人以为「AI 调工具」就该上 LangGraph —— 不是。
现在的 B3 是「模型要工具 → SDK 调 → 结果回灌 → 继续」的**单层循环**，
连分支都没有。LangGraph 是给「流程有分支、有回退、有多个角色」准备的。

#### 13.3 · 成本分析：开销大头不是框架，是流式栈

⚠️ **这一点跟 B5 / B6 无关、永远成立** —— 也是最容易被低估的地方。

| 冲突 | 现状 | 上 LangGraph 会怎样 | 代价 |
| ---- | ---- | ------------------- | ---- |
| **流式协议** | `toUIMessageStream()` → SSE，前端 `useChat` 消费 | `streamEvents()` 事件格式不同 | 🔴 **前端重写** + `messages.parts` 落库格式重写 + 引用卡片重写 |
| **持久化** | `missions` 表（自有 DDL + 索引） | 官方 checkpointer 只有 Postgres / SQLite | 🔴 MySQL 版 saver 自己写 |
| **追踪** | 自建 `traces` / `spans` 两张表 | LangGraph 自带 callback 体系 | 🟠 写适配层，否则 trace 详情页会瞎 |
| **消息模型** | AI SDK v7 的 `UIMessage` | LangChain 的 `BaseMessage[]` | 🟠 要转换层 |
| **工具抽象** | AI SDK `tool({inputSchema, execute})` | LangChain `tool()` | 🟢 包一层即可（`BuiltinTool.execute` 是纯函数，耦合极浅） |

**最容易被低估的是第一行**：现有 SSE 与前端是深度耦合的 ——
`data-tool-call` 是自定义 part、`toUIMessageStream` 必须传 `tools` 才转 part、
前端只渲染自己造的 part。换掉它 = **前端 + 落库 + 引用卡片三层一起动**。

**所以真正的决策不是「LangGraph 好还是手写好」，而是
「多代理 / 可变拓扑这件事，值不值得我重写一遍流式栈」。**

#### 13.4 · B5：已经用手写做完了

2026-10-26 落地：`missions` 表（迁移 `028`）+ 手写工作流引擎（`src/workflows/`）+
闸门接入（`src/tools/execute.ts` 的 `runtime.gate`）+ 三条电商流程
（退款 / 改地址 / 售后工单）。

**为什么手写够用**：三条流程**全线性**（无环、无回退，`tests/unit/workflow-definitions.test.ts`
守着「无环」），LangGraph 相对手写状态机的主要增量（checkpointer 自动续跑 /
并行 fan-out / 多代理 handoff）**当前一条都不需要**。

B5 专属的判据、状态机语义、已知边界见 [12-b §B5.1](./12-b-需求-ai对话能力.md)。

#### 13.5 · B6：已落地，**而且没用 LangGraph**（这是最硬的证据）

**B6 多代理协作（2026-10-26 已落地）** —— 监督者模式：
主 agent 通过一个委派工具 `delegate_to_agent` 把子任务派给专业子代理，
子代理查完把结论回灌，主 agent 综合作答。实现见 `src/agents/` 与 `src/tools/delegate.ts`。

**B6 的三种模式（监督者 / Handoff / Shared State）字面上就是 LangGraph 的主打功能，
但这次实现**一个都没用上**：

| LangGraph 的核心增量 | B6 用到了吗 |
| ------------------- | ----------- |
| `StateGraph`（节点 + 条件边） | ❌ 用「一个委派工具」代替 —— 模型自己决定派给谁，不需要条件边 |
| checkpointing（断点恢复） | ❌ 子代理是**非流式**调用，失败就是失败（整个委派重试即可），不需要 checkpoint |
| `interrupt()` / resume（HITL 暂停） | ❌ **子代理只拿只读工具** —— 写操作留给主 agent，走现有的 HITL 闸门 |
| 并行 fan-out | ❌ 一次只派一个子代理 |
| handoff（子代理移交控制权） | ❌ 子代理之间不接管控制权，靠**共享状态**协作 |

**结论**：监督者模式用「一个委派工具 + 一次非流式 `generateText` + 一张共享状态表」
就够了，**LangGraph 的每一个核心增量都用不上**。这比任何横向对比都更能说明问题。

⚠️ **但有一条翻案条件没变**（§13.6 信号 #1）：
**拓扑要在运行时由租户定义** → 那时候手写撑不住「运行时的图」，**必须上 LangGraph**。
现在 B6 的三个子代理是**平台内置的固定角色**，租户改不了 —— 这正是「用不上」的前提。

### 模块 14 · 多代理协作（Multi-Agent）

**解决什么问题**：单一代理处理复杂任务时上下文太长、专业度不够，需要拆给多个专业代理。

**用到的模式**：

- 监督者模式（Supervisor Pattern）：监督者拆任务给子代理，子代理完成后返回
- Agent Handoff（任务移交）：子代理 A 把控制权交给子代理 B
- Shared State（共享状态）：多个子代理读同一份上下文

**关键代码**：

**子代理分工**：

- 客服代理：主对话、回答用户
- 研究代理：调 RAG、查文档
- 操作代理：调外部系统
- 审核代理：敏感操作二次确认

> **本项目不做**多代理——单代理 + RAG + 记忆 已能跑通客服场景。模块 14 仅做**概念说明**。
> 2026-10-25 复核后定为「未做」（B3 已落地，但多代理的 token 成本是单代理的数倍，
> 且它叠在还没做的 B5 状态机上面），
> 触发条件见 [12-b §B3](./12-b-需求-ai对话能力.md)。
>
> ✅ **2026-10-26 更新：B6 也落地了**（见 §13.5）—— 用**监督者模式**实现的：
> 主 agent 通过一个委派工具把子任务派给专业子代理，子代理的产出经**共享状态**协作。
> **没用 LangGraph**（这次实现本身就是「暂不上」的最好证据 —— 见 §13.3 / §13.5）。
>
> ⚠️ **B6 是需求池里唯一真正的 LangGraph 场景** —— 三种模式（监督者 / Handoff /
> Shared State）字面上就是 LangGraph 的主打功能。**但真到那天也不自动划算**：
> 固定拓扑可以手搓，只有「租户自定义拓扑」才必须上 LangGraph。
> 成本对照与判定见 **[§13.5](#135--b6已落地而且没用-langgraph这是最硬的证据)**。
