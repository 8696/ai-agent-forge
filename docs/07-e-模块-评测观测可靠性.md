**解决什么问题**：怎么知道 Agent 的回答是对的还是错的？每次改 prompt 怎么知道效果有没有变差？

**用到的技术**：

- 评测集管理：上传 CSV / JSONL，按场景分组

- A/B 对比：同一评测集跑两个版本，自动出对比报告
- 评测频率：每天自动跑一次 + 每次 prompt 改动时跑

### 模块 18 · 可观测性（Observability，**自建 trace，不上 OpenTelemetry**）

**解决什么问题**：线上出问题时能快速定位到哪一步出错了；能按用户 / 场景看成本；能看 p95 延迟。

> **简化决定**：之前文档说用 OpenTelemetry 完整链路追踪 + Prometheus + Grafana。**本项目不引这些**——**用 Pino + 自建 trace + MySQL 记录 + 本地文件** 就够本地开发与演示。

**用到的技术**（**自建轻量版**）：

- **链路追踪**：自己写 `tracedAgentLoop()` 包装器，每个 span 写一条 MySQL 记录 + JSON 文件
- **指标（Metrics）**：p50/p95/p99 延迟、QPS、错误率，按分钟聚合写 MySQL（每分钟一行）
- **日志（Logs）**：结构化 JSON 日志（Pino），写 `logs/app-YYYY-MM-DD.log` + `logs/trace-YYYY-MM-DD.jsonl`
- 不用 Langfuse / Prometheus / Grafana / OpenTelemetry Collector

### 模块 19 · 可靠性 / 成本 / 性能（**进程内简化，不上 Redis + 高级限流算法**）

**解决什么问题**：系统不能挂（可靠性）、不能烧钱（成本）、不能慢（性能）。

> **简化决定**：之前文档说「用 Redis 做分布式限流 + 熔断 + 令牌桶 + 漏桶」。**本项目不引 Redis**——**进程内 Map + 简单重试** 就够本地开发与演示。

**用到的技术**（**进程内版**）：

- **限流**：进程内 `Map<key, { count, windowStart }>` 滑动窗口；单进程够用；多进程时升级到 Redis
- **熔断（Circuit Breaker）**：连续失败 N 次短路；进程内计数
- **缓存**：`lru-cache` 进程内缓存（文档检索结果 / LLM 响应）
- **重试**：指数退避 + 抖动（LLM 调用失败自动重试）
- **成本控制**：每租户月度 token 配额；超阈值告警
