## B. 后端技术栈

### B.1 语言与运行时

| 选型       | 版本   | 理由                                                               |
| ---------- | ------ | ------------------------------------------------------------------ |
| Node.js    | 22 LTS | 当前 LTS 版本；原生 fetch、内置测试运行器、性能比 20 LTS 提升 ~20% |
| TypeScript | 5.6    | 类型安全；strict mode + 几条额外严格项                             |
| yarn       | 1.22   | lockfile 稳定、磁盘占用小                                          |

### B.2 框架

| 模块             | 选型                                      | 理由                                                      |
| ---------------- | ----------------------------------------- | --------------------------------------------------------- |
| HTTP 服务        | Koa                                       | 洋葱中间件模型、生态成熟、TypeScript 友好；Express 继任者 |
| Agent 编排       | 手写循环 + LangGraph                      | 手写为主，复杂工作流用 LangGraph                          |
| ORM              | Sequelize                                 | 老牌成熟、迁移工具稳、社区文档全                          |
| 校验             | Zod                                       | 类型 + 运行时校验同源                                     |
| 日志             | Pino                                      | 高性能 JSON 日志                                          |
| 链路追踪（自建） | `tracer.startActiveSpan`-style + 写 MySQL | 自建轻量版，够本地用；要扩展时再上 OpenTelemetry          |

### B.3 中间件

| 中间件   | 选型                                           | 用途                                                | 本地起在哪     |
| -------- | ---------------------------------------------- | --------------------------------------------------- | -------------- |
| 数据库   | MySQL 8.0                                      | 业务数据；JSON 字段、半结构化数据存 MySQL JSON 类型 | Docker Compose |
| 向量库   | Qdrant                                         | 向量检索（RAG 基础 + 重排）                         | Docker Compose |
| 对象存储 | 本地 `./data/uploads/`                         | 上传的文档原文件                                    | 本地磁盘       |
| 链路追踪 | 自建文件（写到 `logs/trace-YYYY-MM-DD.jsonl`） | 调用链路记录，trace 数据存 MySQL + 文件双写         | 本地文件       |

### B.5 Gateway 按「3 套独立子系统」物理隔离（核心架构原则）

> **这是本项目的核心架构原则**——不是「未来要拆」而是「从 Day 1 就分」：代码、URL、数据库 schema、JWT 类型、中间件链**全部按业务边界拆桶**。详见 §17.8（变更同步规则）。

#### B.5.1 三套子系统的边界

本系统的三类用户、三类操作、三类数据是本质不同的，**不应该共用任何代码路径**——所以代码也按三类物理分桶：

| 子系统       | 服务的用户                    | 角色       | 业务边界                                   |
| ------------ | ----------------------------- | ---------- | ------------------------------------------ |
| **system**   | SaaS 平台方（项目开发者自己） | `system`   | 建租户、跨租户运营、查所有租户数据         |
| **admin**    | 客户的运营人员                | `admin`    | 管自己租户内的用户 / 知识库 / 评测 / trace |
| **customer** | 客户的终端用户                | `customer` | 跟 AI 聊（提问题、看自己历史）             |

> **设计原则**：将来即使部署到不同子域（`api.system.xxx.com` / `api.admin.xxx.com` / `api.customer.xxx.com`），或拆成 3 个微服务，**业务逻辑不需要大改**——因为每套子系统的代码、URL、schema、鉴权本来就是独立的。

> **关于 `agent` 角色**：docs/05 的 `users.role` ENUM 保留 `('admin', 'agent', 'customer')` 三值（schema 已存，不动），但**本产品的代码不接受 `agent` 角色登录任何子系统**——AI 客服接待客户，不需要「后台人工坐席」这个角色。`agent` 字段在 DB 里是「留扩展位」，Step 13+ 决定要不要删 ENUM。

#### B.5.2 URL 命名约定

**前后端 URL 前缀完全对齐**（看 URL 就能直接判断属于哪套子系统）：

| 子系统   | 前端路由      | API 路径             | 默认入口（未登录访问 `/`）  |
| -------- | ------------- | -------------------- | --------------------------- |
| system   | `/system/*`   | `/api/v1/system/*`   | —                           |
| admin    | `/admin/*`    | `/api/v1/admin/*`    | —                           |
| customer | `/customer/*` | `/api/v1/customer/*` | ✓（默认走 customer 登录页） |

> **默认入口**是 `customer`（最大众的用户类型），SaaS 开发者从 `/system/login` 直接进，admin 从 `/admin/login` 进。

#### B.5.3 每个子系统的 auth 自闭环

**禁止跨子系统共享 auth 端点**。每个子系统都自带完整的 login / me / change-password 3 件套：

```
POST /api/v1/system/login             {email, password}              → role=system
POST /api/v1/system/me
POST /api/v1/system/change-password   {old_password, new_password}

POST /api/v1/admin/login               {email, password, tenant_code} → role=admin
POST /api/v1/admin/me
POST /api/v1/admin/change-password

POST /api/v1/customer/login            {email, password, tenant_code} → role=customer
POST /api/v1/customer/me
POST /api/v1/customer/change-password
```

**反例（禁止）**：

- ❌ `POST /api/v1/auth/login` + `login_type: 'admin' | 'customer'` 一个端点多种身份
- ❌ 共享的 `change-password` 在 `/api/v1/auth/change-password`（两个子系统共用一个端点）

**好处**：

- SQL `where: { role: 'admin' }` 直接锁死，跨桶登录物理上不可能
- 前端代码：每个登录页只关心自己的桶，TypeScript 类型更清晰
- 将来拆分微服务：每个子系统独立部署、独立扩缩容

#### B.5.4 JWT payload 类型

| 角色       | payload                                           | JWT 类型               |
| ---------- | ------------------------------------------------- | ---------------------- |
| `system`   | `{ sub, role: 'system' }`（无 tenant_id，跨租户） | `SystemJwtPayload`     |
| `admin`    | `{ sub, tenant_id, role: 'admin' }`               | `TenantUserJwtPayload` |
| `customer` | `{ sub, tenant_id, role: 'customer' }`            | `TenantUserJwtPayload` |

> `system` 的 payload **不带 `tenant_id`**——这是它在物理上区别于租户用户的标志。middleware 检查到 `role='system'` 就放行，反之就 401。

**为什么 3 套 Layout 不抽公共组件**：

- 系统端 (`/system/*`) 的菜单是「租户管理 / 平台设置 / 跨租户运营」
- 租户后台 (`/admin/*`) 的菜单是「Dashboard / 知识库 / 用户 / 评测 / Trace / 成本」
- 租户前台 (`/customer/*`) 的菜单是「聊天 / 我的历史」

将来这 3 套 UI 的视觉风格、菜单结构、交互模式都不同——抽公共 Layout 反而是 over-engineering。**布局即业务的物理表达**。

#### B.5.7 鉴权（**每个 Layout 自己做**，没有公共 RequireAuth 组件）

**后端**：3 个独立 `requireXxxUser` 中间件——

| 中间件              | 检查            | 通过后 ctx.state 字段   | 类型                   |
| ------------------- | --------------- | ----------------------- | ---------------------- |
| `requireSystemUser` | role='system'   | `ctx.state.systemUser`  | `SystemJwtPayload`     |
| `requireAdmin`      | role='admin'    | `ctx.state.adminUser`   | `TenantUserJwtPayload` |
| `requireCustomer`   | role='customer' | `ctx.state.accountUser` | `TenantUserJwtPayload` |

**前端**：**没有** `RequireAuth` 公共组件。**每个 Layout 自己在最顶部做 auth 检查**——

```typescript
// 例：web/layouts/admin/AdminLayout.tsx
export function AdminLayout({ children }: { children?: ReactNode }): ReactElement {
  const location = useLocation();

  // login 页不走 auth guard
  if (location.pathname === '/admin/login') {
    return <>{children ?? <Outlet />}</>;
  }

  const user = getCurrentUser();
  if (user === null) {
    window.location.href = '/admin/login';
    return <></>;
  }
  if (user.role !== 'admin') {
    window.location.href = '/';  // 跨子系统：跳回根，由 RootRedirect 重新分流
    return <></>;
  }
  // ... 渲染 Layout
}
```

**为什么每个 Layout 自己做**：

- 3 套 Layout 的 `if (user === null)` 重定向目标不同（`/system/login` / `/admin/login` / `/customer/login`）
- 3 套 Layout 的 role 校验不同（`'system'` / `'admin'` / `'customer'`）
- 抽成公共 `RequireAuth` 反而要传一堆 props 或加 hook，不如直接 inline

> **强约束**（违反即 bug）：
>
> 1. ❌ 路由里手动 `if (role !== ...)` 判断——必须走中间件链
> 2. ❌ 把 system 的端点链上 `requireAdmin`（跨子系统鉴权 = bug）
> 3. ❌ `system/login` 端点接受 `tenant_code` 参数（system 跨租户，不需要）
> 4. ❌ 任何子系统之间共享 `auth.ts` / `change-password.ts`（必须各自闭环）
> 5. ❌ 3 套 Layout 抽公共 `Layout` 组件（layout 是业务的物理表达，抽公共反而 over-engineering）

#### B.5.8 跨子系统跳转的拒绝策略

当一个子系统接收到**不属于自己的 token** 时，**直接 401**（不 redirect，不兜底）：

| 端点                 | 收到的 token          | 行为                                     |
| -------------------- | --------------------- | ---------------------------------------- |
| `/api/v1/system/*`   | role=admin / customer | ✅ 通过（system 端点只看 role='system'） |
| `/api/v1/admin/*`    | role=system           | ❌ 401 `requireSystemUser` 拒            |
| `/api/v1/admin/*`    | role=customer         | ❌ 401 `requireAdmin` 拒                 |
| `/api/v1/customer/*` | role=system           | ❌ 401                                   |
| `/api/v1/customer/*` | role=admin            | ❌ 401                                   |

**好处**：攻击面最小。任何「串号」都会被硬拒，前端想绕过也得重新登录拿正确 token。

#### B.5.9 后续扩展

3 套子系统拆好后，**未来如果要把某一套拆成微服务**（比如把 `system` 子系统独立部署到 `admin.goaichat.top`），改动范围只在：

- 部署配置（域名 / 端口 / CORS allow-list）
- 前端 axios 的 `baseURL` 按子域名切

**不需要改**：
