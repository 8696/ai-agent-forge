# 09 · 观测方案

> **状态**：D2 已落地（2026-10-24）。本文档是「观测什么、告警什么」的规格；
> 落地细节（接口 / 表 / 页面）见 [12-d-需求-运维稳定.md §D2](./12-d-需求-运维稳定.md)。
>
> 全部本地实现，**不上 OpenTelemetry**：trace 数据写 MySQL + 本地 JSON 文件，metric 写 MySQL 聚合表，log 用 Pino。

## 9.1 链路追踪（Trace）

- 每次用户请求一个 trace，每个 Agent 步骤一个 span
- span 属性：user_id、session_id、tenant_id、step_name、input_tokens、output_tokens、duration_ms、tool_calls
- **自建 trace 包装器**（`src/services/trace.ts`）：每个 span 写 MySQL 一行 + 同步写到 `logs/trace-YYYY-MM-DD.jsonl` 本地文件
- 不引入 Langfuse / Jaeger / Tempo / OpenTelemetry Collector

> **落地偏差**：
> - 包装器放在 **`src/services/trace.ts`**（不是设计稿写的 `src/observability/trace.ts`）：
>   它是「业务链路上的旁路采集」，跟 `chat.ts` / `cost-tracking.ts` 这些 service 是同一层
> - **span 属性改了**：设计稿列的 `tool_calls` / `step_name` 没有照搬 ——
>   实际字段是 `id` / `trace_id` / `tenant_id` / `parent_span_id` / `name` / `kind` /
>   `status` / `duration_ms` / `input` / `output` / `error_message` / `started_at` / `ended_at`。
>   `user_id` / `session_id` / `token` / `cost` **在 trace 行上**（不在 span 上）——
>   一条 trace 就是一次对话，挂在 trace 上比在 5 个 span 上各挂一份省事
> - `input` / `output` 只存**摘要**（命中条数、token 数这类），**不存对话正文** ——
>   正文在 `messages` 表里，再复制一份等于把敏感数据多存一遍
> - **一次对话对应 5 个 span**：
>   `http.request`（路由）→ `security.guard`（安全审核）→ `retrieval.search`（知识库检索）
>   → `llm.generate`（模型调用）→ `cost.record`（成本记账）
> - **trace 是「结束时一次性写」**：内存里攒，结束时一个事务里写 trace + spans（2 次 INSERT）。
>   代价是进程在请求中途被 kill 就丢这一条 trace
> - 「同步写到本地文件」是 `appendFile` 异步追加（一行一条 JSON），写失败只 debug 一行
> - 开关：`TRACE_ENABLED`（总开关，关掉后业务链路拿到空实现 handle）+ `TRACE_FILE_ENABLED`（只关 JSONL 副本）

> 什么时候升级到 OpenTelemetry：多进程部署 / 跨服务追踪 / 需要 OTel 生态可视化工具时再升级。

## 9.2 指标（Metric）

- 关键 SLI：
    - 可用性：99.5%
    - p95 延迟：≤ 3 秒
    - 错误率：≤ 1%
    - 单条成本：≤ $0.05
- 指标按分钟聚合写到 MySQL（`metrics_minutely` 聚合表）⏳ **未做**
- 后台首页直接读 MySQL 渲染指标卡 + 趋势图 ✅
- 不引入 Prometheus / Grafana

> **落地偏差**：
> - **`metrics_minutely` 分钟级聚合表没做**。指标现在是**实时聚合查询**算出来的
>   （`GET /api/v1/admin/observability/summary`），数据量大到百万级 trace 时会变慢，
>   届时需要按分钟预聚合
> - p95 用 MySQL 8 的窗口函数**精确**算（`ROW_NUMBER() OVER (ORDER BY duration_ms)`），
>   不是抽样近似
> - 「后台首页」现在指**顶栏告警条 + 「观测」页**；Dashboard 页（`/admin/dashboard`，
>   4 张指标卡 + 2 张趋势图）本期没做 —— 指标接口 `/observability/summary` 已经齐了，
>   接页面是纯前端工作

## 9.3 日志（Log）

- 结构化 JSON 日志（Pino）
- 日志级别：ERROR / WARN / INFO / DEBUG
- 日志文件：`./logs/app-YYYY-MM-DD.log`
- 不引入 ELK / Loki

> **落地偏差**：
> - **没有 app 日志文件**：Pino 只写 stdout，部署时由进程管理器 / 容器收集。
>   （`./logs/` 目录只放 D2 的 trace JSONL 副本）
> - 唯一落盘的日志是 `logs/trace-YYYY-MM-DD.jsonl`（trace 副本，不是应用日志）

## 9.4 告警

- 错误率 > 5%（5 分钟窗口）→ 控制台告警条 + 可选发邮件 ⚠️ 窗口改成「今天」
- p95 延迟 > 5 秒 → 控制台告警条 ✅
- 单条对话成本 > $0.5 → 控制台告警条 ✅
- 评测分数周环比跌 10% → 控制台告警条 ⚠️ 基准改成「同评测集的上一次跑批」
- 不引入短信 / Slack（本地运行没有这些渠道）

> **落地说明**：
> - 全部接进**租户后台顶栏告警条**（`docs/04-c-ui-后台管理页面.md` §5.0，
>   数据源 `GET /api/v1/admin/config/alerts`）
> - **窗口偏差**：错误率 / p95 / 单条成本看的是**今天**（不是 5 分钟）。
>   5 分钟窗口在后台这种「看一眼」的用法下几乎永远不触发（错一次就恢复了）；
>   真要做 5 分钟窗口需要 §9.2 的分钟级聚合表
> - **评测分数的比较基准是「同评测集的上一次跑批」**（不是周环比）：
>   同一个评测集的前后两次才有可比性
> - **阈值是代码里的常量**（`src/services/alerts.ts`），后台不能改规则，
>   也没有「触发次数」的历史视图 —— `docs/04-c` §5.7.4 的「告警规则」页本期没做
> - 「可选发邮件」没做
