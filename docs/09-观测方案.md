# 09 · 观测方案

> 全部本地实现，**不上 OpenTelemetry**：trace 数据写 MySQL + 本地 JSON 文件，metric 写 MySQL 聚合表，log 用 Pino。

## 9.1 链路追踪（Trace）

- 每次用户请求一个 trace，每个 Agent 步骤一个 span
- span 属性：user_id、session_id、tenant_id、step_name、input_tokens、output_tokens、duration_ms、tool_calls
- **自建 trace 包装器**（`src/observability/trace.ts`）：每个 span 写 MySQL 一行 + 同步写到 `logs/trace-YYYY-MM-DD.jsonl` 本地文件
- 不引入 Langfuse / Jaeger / Tempo / OpenTelemetry Collector

> 什么时候升级到 OpenTelemetry：多进程部署 / 跨服务追踪 / 需要 OTel 生态可视化工具时再升级。

## 9.2 指标（Metric）

- 关键 SLI：
    - 可用性：99.5%
    - p95 延迟：≤ 3 秒
    - 错误率：≤ 1%
    - 单条成本：≤ $0.05
- 指标按分钟聚合写到 MySQL（`metrics_minutely` 聚合表）
- 后台首页直接读 MySQL 渲染指标卡 + 趋势图
- 不引入 Prometheus / Grafana

## 9.3 日志（Log）

- 结构化 JSON 日志（Pino）
- 日志级别：ERROR / WARN / INFO / DEBUG
- 日志文件：`./logs/app-YYYY-MM-DD.log`
- 不引入 ELK / Loki

## 9.4 告警

- 错误率 > 5%（5 分钟窗口）→ 控制台告警条 + 可选发邮件
- p95 延迟 > 5 秒 → 控制台告警条
- 单条对话成本 > $0.5 → 控制台告警条
- 评测分数周环比跌 10% → 控制台告警条
- 不引入短信 / Slack（本地运行没有这些渠道）
